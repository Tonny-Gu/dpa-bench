# Bridging Intra- and Inter-node Networks with Reprogrammed GPU Copy Engines

## Abstract

- Modern distributed GPU systems increasingly rely on two high-performance but poorly synchronized communication domains:
  - **Intra-node GPU fabrics**, such as NVLink / NVSwitch, which provide high-bandwidth GPU-to-GPU movement inside a node.
  - **Inter-node RDMA networks**, such as InfiniBand / RoCE, which move data across machines with low CPU overhead.

- Existing systems often bridge these domains through:
  - **SM-mediated relay kernels**, where GPU Streaming Multiprocessors execute forwarding logic.
  - **CPU proxy paths**, where the GPU exposes readiness to the host and the CPU posts RDMA work.
  - **Coarse runtime-level Copy Engine APIs**, where data movement can be offloaded but progress is visible only at stream, event, or batch granularity.

- This proposal argues that the missing primitive is **fine-grained, host-visible Copy Engine progress**:
  - Copy Engines can move data across intra-node GPU links without consuming SM cycles.
  - RDMA NICs can directly read GPU memory using GPUDirect RDMA.
  - What is missing is a way to know, at chunk granularity, when a Copy Engine has produced data that is safe for RDMA transmission.

- We propose to build a restricted Copy Engine command-submission shim that:
  - Constructs Copy Engine push buffers directly.
  - Inserts per-chunk semaphore release commands after each Copy Engine DMA.
  - Lets a CPU-side RDMA bridge poll Copy Engine progress and post RDMA work requests for completed chunks.
  - Preserves Copy Engine doorbell batching while exposing fine-grained progress.

- The target contribution is not “Copy Engines can copy data.” That part is already known. The target contribution is:
  - **Copy Engine progress can become a scheduling signal for pipelining NVLink-domain movement with RDMA-domain movement, without using SMs in the data relay path.**

## 1. Motivation

- Multi-GPU systems have evolved into dense intra-node GPU fabrics:
  - NVIDIA NVLink / NVSwitch provide high-bandwidth GPU-to-GPU communication and are now central to large-scale AI systems. NVIDIA describes NVLink and NVLink Switch as scale-up interconnects for large model parallelism and high-bandwidth GPU communication. ([NVIDIA NVLink](https://www.nvidia.com/en-us/data-center/nvlink/))
  - Across nodes, systems still rely on scale-out networks such as InfiniBand or Ethernet/RoCE. NVIDIA’s NVSHMEM / GPUDirect Async discussion explicitly frames modern systems as using NVLink inside nodes and InfiniBand across nodes. ([NVIDIA Developer Blog, 2022](https://developer.nvidia.com/blog/improving-network-performance-of-hpc-systems-using-nvidia-magnum-io-nvshmem-and-gpudirect-async/))

- RDMA was designed around NIC-side work queues, queue pairs, and host or device-visible memory registration:
  - User-space applications post Work Queue Elements (WQEs) into Queue Pairs (QPs), and RNICs report completion through Completion Queues (CQs). ([Flor, OSDI 2023](https://www.usenix.org/system/files/osdi23-li-qiang.pdf))
  - GPUDirect RDMA enables a direct PCIe path between NVIDIA GPUs and third-party peer devices, including network interfaces, but it also comes with topology and platform constraints such as shared PCIe root-complex requirements and IOMMU restrictions. ([NVIDIA GPUDirect RDMA Documentation](https://docs.nvidia.com/cuda/gpudirect-rdma/))

- The interoperation problem is not only “can the NIC read GPU memory?”
  - The harder systems problem is: **how do we schedule and synchronize data movement across NVLink and RDMA when they are controlled by different engines, different software stacks, and different completion mechanisms?**
  - CXL points toward cache-coherent CPU-device and memory-device interoperability, but current GPU communication stacks still largely rely on explicit mechanisms such as NVLink, GPUDirect RDMA, CUDA streams/events, and RDMA verbs. CXL’s own description emphasizes coherent CPU-device and CPU-memory-space sharing, which is a different abstraction from today’s explicit GPU/NIC command paths. ([Compute Express Link](https://computeexpresslink.org/about-cxl/))

- RDMA itself is not always operationally uniform:
  - Microsoft’s Azure RDMA deployment experience reports that even NICs from the same vendor can show different behaviors that cause interoperability issues, and that device diversity complicates cloud-scale RDMA operation. ([Microsoft Research RDMA Experience Report](https://www.microsoft.com/en-us/research/wp-content/uploads/2023/03/RDMA_Experience_Paper_TR-1.pdf))
  - Flor, an OSDI 2023 system, studies heterogeneous RNIC deployments and reports performance gaps across different RNIC vendors and generations. ([Flor, OSDI 2023](https://www.usenix.org/system/files/osdi23-li-qiang.pdf))

## 2. Existing Bridges Between NVLink and RDMA

- **NCCL PXN, 2022**
  - NCCL PXN lets a GPU communicate with a non-local NIC through NVLink and then PCIe, avoiding slower CPU-socket traversal paths in some topologies.
  - Example:
    - Before: `GPU1 -> PCIe -> NUMA1 -> UPI/QPI -> NUMA0 -> PCIe -> NIC0`
    - After: `GPU1 -> NVLink -> GPU0 -> PCIe -> NIC0`
  - NCCL PXN also leverages rail-optimized topologies, where NICs with the same local rank across nodes connect to the same leaf switch, reducing cross-rail or spine traffic. ([NVIDIA Developer Blog, 2022](https://developer.nvidia.com/blog/doubling-all2all-performance-with-nvidia-collective-communication-library-2-12/))

```text
Bad GPU-NIC affinity:

  GPU1 --PCIe--> NUMA1 --UPI/QPI--> NUMA0 --PCIe--> NIC0

PXN-style relay:

  GPU1 --NVLink--> GPU0 --PCIe--> NIC0
```

- **DeepEP / Expert Parallel Dispatch, 2025**
  - DeepEP targets Mixture-of-Experts communication, especially dispatch and combine operations.
  - Its README describes the library as focusing on high-throughput and low-latency all-to-all GPU kernels for MoE dispatch/combine, designed for zero or minimal SM occupation. ([DeepEP GitHub, 2025](https://github.com/deepseek-ai/DeepEP))
  - Microsoft’s Azure DeepEP performance writeup describes specialized asymmetric-domain forwarding kernels between NVLink and RDMA/InfiniBand domains, where tokens are transmitted over InfiniBand to GPUs with matching in-node indices and then forwarded through NVLink to target experts. That writeup says 20 SMs are sufficient to saturate both domains. ([Microsoft Azure HPC Blog, 2025](https://techcommunity.microsoft.com/blog/azurehighperformancecomputingblog/achieving-optimal-performance-for-deepseek-expert-parallelism-deepep-on-azure/4414699))

```text
MoE token deduplication / forwarding:

  remote token --RDMA--> GPU0 --NVLink copy/forward--> GPU1, GPU2, GPU3
```

- **FuseLink, 2025**
  - FuseLink integrates high-speed intra-server links with inter-server communication and uses GPUs to relay traffic to idle NICs.
  - Its OSDI 2025 abstract reports up to 212 GB/s bandwidth between two inter-server GPUs and improvements for LLM serving, MoE training, and recommendation workloads. ([FuseLink, OSDI 2025](https://www.usenix.org/conference/osdi25/presentation/ren))

```text
Multi-NIC relay pattern:

  GPU0 --NVLink--> GPU1 --> NIC1
    |              GPU2 --> NIC2
    |              GPU3 --> NIC3
    +--------------------> NIC0
```

- These systems show that the idea of crossing NVLink and RDMA domains is valuable and practical.
  - However, many relay-style paths still rely on GPU kernels, SM-mediated forwarding, or device-side communication control in performance-sensitive regions.
  - This creates interference with background compute, especially when communication needs to be fine-grained and overlapped with model execution.

## 3. Why Copy Engines Are Attractive

- NVIDIA GPUs include dedicated Copy Engines that can move data between GPU memory, CPU memory, and peer GPUs.
  - Reverse-engineering and GPU scheduling work describes modern NVIDIA GPUs as having multiple engines, including Copy Engines, with data movement handled separately from the Compute/Graphics Engine. ([Demystifying NVIDIA GPU Internals, RTAS 2024](https://www.cs.unc.edu/~jbakita/rtas24.pdf))

- NCCL 2.28 introduced Copy Engine based collectives:
  - NVIDIA describes these CE collectives as using Copy Engines to drive NVLink transfers, reducing SM resource contention.
  - NCCL’s CE-based collectives target data-movement collectives such as AllToAll and AllGather, and NVIDIA describes them as zero-SM operation within the NVLink domain. ([NVIDIA Developer Blog, 2025](https://developer.nvidia.com/blog/fusing-communication-and-compute-with-new-device-api-and-copy-engine-collectives-in-nvidia-nccl-2-28/))

- NCCL 2.28 also introduced the Device API and GPU-Initiated Networking:
  - The Device API supports Load/Store Accessible communication, Multimem, and GIN.
  - GIN enables GPU-initiated network operations, with documentation requirements including CUDA, GPU, NIC, rdma-core, GPUDirect RDMA, and topology constraints. ([NVIDIA Developer Blog, 2025](https://developer.nvidia.com/blog/fusing-communication-and-compute-with-new-device-api-and-copy-engine-collectives-in-nvidia-nccl-2-28/))
  - NCCL’s GIN documentation exposes device-callable one-sided transfer APIs and multiple GIN contexts for spreading traffic across connections. ([NVIDIA NCCL Device GIN Documentation](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/api/device_gin.html))

- Recent MoE work also validates Copy Engine usefulness:
  - FEPLB, 2026, uses NVLink Copy Engines for intra-node MoE load balancing on Hopper, explicitly relying on SM-free Copy Engine movement within the NVLink domain. ([FEPLB, arXiv 2026](https://arxiv.org/html/2604.19654v1))

- These trends point to a clear opportunity:
  - Copy Engines are becoming a legitimate communication substrate.
  - Current public APIs mostly expose them as **bulk movement engines**, not as **fine-grained progress producers**.
  - Our proposal focuses exactly on that gap.

## 4. Research Claim

- Existing Copy Engine abstractions are good at batching movement, but weak at exposing progress.

- We claim that the key missing primitive is:

> **Fine-grained, host-visible Copy Engine progress that can be used to schedule RDMA operations.**

- The proposed system turns Copy Engine progress into a bridge between two communication domains:

```text
NVLink / CE domain                         RDMA / NIC domain

  CE copies chunk 0
        |
        v
  CE releases semaphore = 0  ----+
                                 |
  CE copies chunk 1              | CPU polls progress
        |                        |
        v                        v
  CE releases semaphore = 1 --> post RDMA WRs for completed chunks
                                 |
                                 v
                          NIC reads GPU memory via GPUDirect RDMA
```

- This changes the story from:

> Use Copy Engines to move RDMA/NVLink traffic.

- Into:

> Use fine-grained Copy Engine progress as the missing clock signal for pipelining NVLink-domain and RDMA-domain transfers.

## 5. Challenges

### C1. Fine-grained completion granularity

- Public CUDA APIs expose completion at stream, event, or batch granularity.
- NVLink/RDMA pipelining needs **per-chunk progress**:
  - Split a buffer into KB-scale or MB-scale chunks.
  - Start RDMA for chunk `i` as soon as the Copy Engine finishes producing chunk `i`.
  - Avoid waiting for the whole Copy Engine batch to complete.

- `cudaMemcpyBatchAsync` is close, but not enough:
  - CUDA 12.8 added batch async memory copy APIs for variable-sized transfers between multiple source and destination buffers. ([CUDA Toolkit 12.8 Release Notes](https://docs.nvidia.com/cuda/archive/12.8.2/cuda-toolkit-release-notes/index.html))
  - CUDA’s runtime documentation says the batch as a whole executes in stream order, but copies inside the batch are not guaranteed to execute in a specific order; dependent copies inside a batch are undefined behavior. ([CUDA Runtime API Documentation](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY.html))
  - This makes it difficult to use public batch APIs for ordered per-chunk progress.

### C2. GPU command submission overhead

- A naïve design would submit one Copy Engine operation per chunk:
  - `cudaMemcpyAsync(chunk 0)`
  - `cudaEventRecord(event 0)`
  - `cudaMemcpyAsync(chunk 1)`
  - `cudaEventRecord(event 1)`
  - …

- This is likely too expensive because each tiny operation can introduce CPU-side runtime/driver overhead and GPU command-submission overhead.
  - NVIDIA’s CUDA Graphs material describes GPU operation submission overhead as microsecond-scale and motivates graphs as a way to launch multiple operations through one CPU operation. ([NVIDIA CUDA Graphs Blog, 2019](https://developer.nvidia.com/blog/cuda-graphs/))
  - CUDA Graphs reduce repeated launch overhead, but graph construction and instantiation remain separate preprocessing steps whose cost depends on graph structure. NVIDIA’s CUDA 12.6 graph performance writeup explicitly discusses construction, instantiation, and launch overhead improvements. ([NVIDIA CUDA Graphs Performance Blog, 2024](https://developer.nvidia.com/blog/constant-time-launch-for-straight-line-cuda-graphs-and-other-performance-enhancements/))

- For our use case, we need:
  - One GPU doorbell for many Copy Engine commands.
  - Per-chunk semaphore release inside the batched command stream.
  - Progress visibility without one CUDA event per chunk.

### C3. Cross-domain ordering and visibility

- The correctness condition is subtle:

```text
CE writes GPU memory
CE executes release fence
CE writes host-visible semaphore
CPU observes semaphore
CPU posts RDMA work request
NIC reads GPU memory
```

- The system must ensure:
  - The CPU does not post RDMA before the Copy Engine has completed the chunk.
  - The NIC does not read stale or partially written GPU data.
  - The ordering between Copy Engine writes, semaphore updates, and GPUDirect RDMA reads is valid on the target topology.

- GPUDirect RDMA itself has topology requirements:
  - NVIDIA documents that GPU and third-party devices often need to share the same upstream PCIe root complex.
  - It also documents that GPUDirect RDMA relies on physical addresses being the same from different PCI devices’ point of view, making non-1:1 IOMMU translation incompatible unless disabled or configured for pass-through. ([NVIDIA GPUDirect RDMA Documentation](https://docs.nvidia.com/cuda/gpudirect-rdma/))

## 6. Host-GPU Interface

### 6.1 CUDA streams are not the hardware scheduling primitive

- CUDA programmers see streams.
- The CUDA Runtime and User Mode Driver lower streams into hardware-facing structures:
  - Channels
  - Runlists
  - GPFIFO rings
  - Push buffers
  - Engine-specific command streams
  - Cross-channel semaphores

- Prior work on NVIDIA GPU internals shows that GPU scheduling involves channels, runlists, and engines, and that every GPU-engine-using operation goes through a channel. ([Demystifying NVIDIA GPU Internals, RTAS 2024](https://www.cs.unc.edu/~jbakita/rtas24.pdf))
- Recent command-stream reverse engineering describes NVIDIA command submission as a path where the driver writes pushbuffer commands, enqueues GPFIFO entries, advances `GP_PUT`, and rings a doorbell; then PBDMA fetches the GPFIFO entry and pushbuffer commands. ([Revealing NVIDIA Closed-Source Driver Command Streams, arXiv 2026](https://arxiv.org/html/2604.26889v1))

```text
+------------------+       +----------------------+       +-----------------------+
| User Application |       | CUDA Runtime & UMD   |       | GPU                   |
|                  |       |                      |       |                       |
|  Stream 0 -------+-----> |                      |       |  Runlist 0 -> Compute |
|  Stream 1 -------+-----> |  Scheduler           | ----> |  Runlist 1 -> CE0     |
|                  |       |    |                 |       |  Runlist 2 -> CE1     |
+------------------+       |    v                 |       +-----------------------+
                           |  Ch0  Ch1  Ch2  Ch3  |
                           +---|----|----|----|---+
                               |    |    |    |
                               |    |    |    +------> Runlist 2
                               |    |    +-----------> Runlist 1
                               +----+----------------> Runlist 0
```

- In this view:
  - A CUDA stream is a software abstraction.
  - A channel is closer to the hardware submission unit.
  - A runlist groups channels for scheduling onto engines.
  - A Copy Engine command is encoded into pushbuffer methods consumed by the GPU front-end and dispatched to the Copy Engine.

### 6.2 GPFIFO and push buffers

- Each channel contains or refers to:
  - A GPFIFO ring buffer.
  - `GP_PUT`, the producer index.
  - `GP_GET`, the consumer index.
  - Push buffer segments containing actual engine commands.

```text
Channel

  USERD:
    GP_PUT = producer index
    GP_GET = consumer index

  GPFIFO ring:
    +----------+      +-----------------------------+
    | entry 0  | ---> | Push Buffer A               |
    +----------+      |  cmd0 | cmd1 | cmd2 | ...   |
    | entry 1  | ---> +-----------------------------+
    +----------+
    | entry 2  | ---> +-----------------------------+
    +----------+      | Push Buffer B               |
    |   ...    |      |  cmd0 | cmd1 | ...          |
    +----------+      +-----------------------------+
```

- A typical GPU command submission path is:

```text
CPU / UMD:
  1. Write pushbuffer commands.
  2. Fill one GPFIFO entry pointing to the pushbuffer segment.
  3. Advance GP_PUT.
  4. Ring GPU doorbell through MMIO.

GPU / PBDMA:
  5. Fetch GP_PUT / channel state.
  6. Fetch GPFIFO entry.
  7. Fetch pushbuffer command stream.
  8. Parse commands and dispatch them to Compute / Copy Engine.
```

- The command-stream reverse-engineering paper describes this two-level hierarchy and the PBDMA fetch path in detail: pushbuffer commands hold raw engine command streams, GPFIFO entries point to pushbuffer segments, and the doorbell commits new work to the GPU. ([Revealing NVIDIA Closed-Source Driver Command Streams, arXiv 2026](https://arxiv.org/html/2604.26889v1))

### 6.3 GPU doorbell vs RDMA NIC doorbell

- GPU and RDMA NIC submission look superficially similar:
  - Both use user-space command construction.
  - Both can notify hardware through MMIO doorbells.
  - Both avoid a kernel transition on the hot submission path once resources are mapped.

- But the post-doorbell paths are different.

```text
GPU Copy Engine submission:

  CPU
   |
   | MMIO write: GPU doorbell
   | token ~= channel / runlist identifier
   v
  GPU PBDMA
   |
   | read USERD / GP_PUT
   | read GPFIFO entry
   | read Push Buffer commands
   v
  Copy Engine
   |
   | execute CE_DMA_LAUNCH / semaphore / fence methods
   v
  GPU memory / host-visible semaphore
```

```text
RDMA NIC submission:

  CPU
   |
   | write WQE(s) into Send Queue
   | update doorbell record
   | MMIO write: NIC doorbell
   | token ~= QP / opcode / old SQ tail / new SQ length
   v
  RNIC
   |
   | DMA-read WQE batch from SQ
   v
  RDMA engine
   |
   | read GPU memory through GPUDirect RDMA
   | transmit packet(s)
   v
  remote node
```

- RDMA systems have mature batching techniques:
  - Doorbell batching lets multiple WQEs use one Doorbell MMIO.
  - Kalia et al. describe doorbell batching as reducing CPU-generated MMIOs and PCIe transactions; they also distinguish WQE-by-MMIO from Doorbell mode, where the NIC reads WQEs through DMA. ([Kalia et al., ATC 2016](https://www.usenix.org/system/files/conference/atc16/atc16_paper-kalia.pdf))
  - The same paper notes that Mellanox terminology uses “BlueFlame” for WQE-by-MMIO and “Doorbell” for the DMA-read path. ([Kalia et al., ATC 2016](https://www.usenix.org/system/files/conference/atc16/atc16_paper-kalia.pdf))

- Our hypothesis:
  - **GPU Copy Engine submission is even more sensitive to unbatched doorbells than RNIC posting**, because a GPU doorbell triggers a multi-stage PBDMA path through `USERD`, GPFIFO, and pushbuffer fetches.
  - Therefore, we should not submit one Copy Engine operation per chunk.
  - Instead, we should submit one batched Copy Engine pushbuffer that contains many chunk copies and many per-chunk progress releases.

## 7. CUDA Runtime and UMD API Limitations

- CUDA provides several ways to reduce launch overhead:
  - CUDA streams and events.
  - CUDA Graphs.
  - Batched memory-copy APIs such as `cudaMemcpyBatchAsync`.

- However, these APIs are not designed for our exact control pattern:
  - CUDA Graphs can batch work and reduce repeated launch overhead, but graph capture/instantiation is still a graph-level mechanism.
  - `cudaMemcpyBatchAsync` can batch many copies, but its public completion model is batch-level or stream-level, not per-copy progress.
  - CUDA documents that copies within a batch are not guaranteed to execute in order, and dependent copies within a batch are undefined behavior. ([CUDA Runtime API Documentation](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY.html))

- For NVLink/RDMA pipelining, the awkward part is:

```text
Desired:
  after chunk 0 copied by CE -> RDMA chunk 0 immediately
  after chunk 1 copied by CE -> RDMA chunk 1 immediately
  after chunk 2 copied by CE -> RDMA chunk 2 immediately

Public batch API:
  submit many copies
  observe completion of the whole batch / stream event
```

- The missing API is not simply “batched memcpy.”
- The missing API is:

```text
batched CE command submission
+ ordered per-chunk release fence
+ host-visible progress counter
```

## 8. Preliminary Investigation: CUDA Async Operations

- We use `geohot/cuda_ioctl_sniffer` to inspect CUDA Runtime / UMD interaction with the GPU.
  - The repository states that it can launch a CUDA kernel without using the CUDA driver runtime and includes code for pushing command queues and replacing parts of CUDA initialization. ([cuda_ioctl_sniffer GitHub](https://github.com/geohot/cuda_ioctl_sniffer))
  - Recent command-stream work also shows that customized commands can be injected by identifying pushbuffer, GPFIFO, and semaphore buffers, then writing directly and ringing the doorbell. ([Revealing NVIDIA Closed-Source Driver Command Streams, arXiv 2026](https://arxiv.org/html/2604.26889v1))

- We inspect a simple sequence:

```cuda
cudaMemcpyBatchAsync(dst=[...], src=[...], kind=H2D, stream=0);
cudaEventRecord(event, stream=0);
```

- Observed behavior for `cudaMemcpyBatchAsync`:
  - One new GPFIFO entry on a Copy Engine channel.
  - One pushbuffer command sequence roughly of the form:

```text
[
  CE_DMA_LAUNCH,
  CE_DMA_LAUNCH,
  ...
  CE_SET_SEMAPHORE,
  CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE
]
```

  - Each `(dst, src)` pair becomes one Copy Engine DMA launch.
  - The final semaphore is internal to CUDA’s stream/event machinery.
  - One GPU doorbell submits the batched CE command stream.

- Observed behavior for `cudaEventRecord`:
  - One new GPFIFO entry on a Compute channel.
  - One pushbuffer command sequence roughly of the form:

```text
[
  GPFIFO_WAIT_AND_ACQUIRE_SEMAPHORE,
  COMP_SET_REPORT_SEMAPHORE_AND_RELEASE
]
```

  - The compute channel waits for the Copy Engine channel’s internal semaphore.
  - The compute channel writes a user-visible event/report semaphore.
  - `cudaEventQuery` eventually observes this user-visible completion.

- This shows that CUDA stream ordering is translated into cross-channel semaphore synchronization:

```text
CUDA stream order:

  cudaMemcpyBatchAsync(...)
  cudaEventRecord(...)

Hardware-level lowering:

  CE channel:
    CE_DMA_LAUNCH x N
    internal semaphore release

  Compute channel:
    wait internal semaphore
    write user-visible event semaphore
```

| API call | Hardware-level artifact | Channel |
|---|---|---|
| `cudaMemcpyBatchAsync` | GPFIFO entry + CE pushbuffer with many `CE_DMA_LAUNCH` commands and one internal semaphore release | Copy Engine |
| `cudaEventRecord` | GPFIFO entry + compute pushbuffer waiting on CE semaphore and writing user-visible report semaphore | Compute |
| `cudaEventQuery` | Host-side polling of event/report state | Host/runtime |

- This is almost what we need, except the progress signal is too coarse:
  - CUDA emits many DMA commands.
  - CUDA releases one completion signal at the end.
  - We want one completion signal per chunk, while preserving one batched doorbell.

## 9. Proposed Design

### 9.1 Key idea

- Instead of using public CUDA batch APIs, construct a Copy Engine pushbuffer like this:

```text
[
  CE_DMA_LAUNCH(chunk 0),
  CE_SET_SEMAPHORE(value = 0),
  CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE,

  CE_DMA_LAUNCH(chunk 1),
  CE_SET_SEMAPHORE(value = 1),
  CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE,

  CE_DMA_LAUNCH(chunk 2),
  CE_SET_SEMAPHORE(value = 2),
  CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE,

  ...
]
```

- The Copy Engine command stream itself becomes the progress generator:
  - Each chunk copy is followed by a release fence and semaphore update.
  - The semaphore value is the highest completed chunk index.
  - The CPU polls this semaphore.
  - When the value advances, the CPU posts RDMA WRs for newly completed chunks.

```text
Copy Engine timeline:

  copy c0 | release sem=0 | copy c1 | release sem=1 | copy c2 | release sem=2 | ...

CPU / RDMA bridge:

  poll sem
    sem = 0  -> post RDMA(c0)
    sem = 1  -> post RDMA(c1)
    sem = 2  -> post RDMA(c2)
```

### 9.2 Restricted CE shim

- We do not attempt to replace CUDA UMD.
- We build a narrow shim for Copy Engine command submission only.

- The shim handles:
  - Copy Engine channel setup or discovery.
  - GPFIFO and pushbuffer construction.
  - Copy Engine DMA commands.
  - Semaphore commands.
  - Release fences.
  - Doorbell notification.

- The shim does **not** handle:
  - General CUDA stream scheduling.
  - Compute kernel launch.
  - General CUDA Graph semantics.
  - Full driver replacement.
  - Multi-rail aggregation in this proposal, because the current testbed does not have the required multi-NIC / multi-rail topology.

- Conceptually:

```text
Application / benchmark
        |
        v
+-----------------------------+
| CE-Progress Shim            |
|                             |
| - build CE pushbuffer       |
| - insert per-chunk fence    |
| - insert per-chunk sem      |
| - ring GPU doorbell once    |
+-----------------------------+
        |
        v
+-----------------------------+
| RDMA Posting Bridge         |
|                             |
| - poll CE progress sem      |
| - batch RDMA WRs            |
| - ring NIC doorbell         |
+-----------------------------+
        |
        v
   RDMA NIC reads GPU memory
```

### 9.3 RDMA bridge

- The CPU-side bridge:
  - Polls a host-visible semaphore updated by the Copy Engine.
  - Converts progress deltas into RDMA work requests.
  - Uses doorbell batching and unsignaled WRs where appropriate.
  - Pins the polling thread near the GPU/NIC NUMA domain.
  - Uses GPUDirect RDMA registered GPU buffers for NIC-side reads.

- The bridge intentionally keeps the CPU in the control path for the first design:
  - This avoids requiring GPU-initiated NIC doorbell access.
  - It preserves compatibility with standard RDMA NICs.
  - It makes the design easier to debug and evaluate.
  - The tradeoff is that CPU polling and RDMA posting rate become key performance limits.

- This tradeoff is real:
  - NVIDIA’s GPUDirect Async / NVSHMEM writeup notes that CPU proxy paths continuously consume CPU cycles and cannot reach peak NIC throughput for fine-grained transfers because the proxy thread becomes a bottleneck. ([NVIDIA Developer Blog, 2022](https://developer.nvidia.com/blog/improving-network-performance-of-hpc-systems-using-nvidia-magnum-io-nvshmem-and-gpudirect-async/))
  - Our system avoids SM relay, but it must quantify whether CPU-side RDMA posting eats the benefit. Tiny chunks may summon the CPU goblin; the benchmark must catch it before it eats the graph.

## 10. Evaluation Plan

### 10.1 Microbenchmarks

- **M1. Copy Engine submission overhead**
  - Compare:
    - `cudaMemcpyAsync` per chunk.
    - `cudaMemcpyBatchAsync`.
    - CUDA Graph with memcpy/event nodes.
    - Custom CE pushbuffer with per-chunk semaphores.
  - Metrics:
    - Submission latency.
    - Number of GPU doorbells.
    - Achieved copy bandwidth.
    - CPU overhead per chunk.
    - Sensitivity to chunk count and chunk size.

- **M2. Per-chunk progress latency**
  - Measure:
    - Time from CE finishing chunk `i` to host observing semaphore `i`.
    - Polling overhead and cache behavior.
    - Latency distribution under different polling thread placements.
  - Sweep:
    - Semaphore memory placement.
    - Polling interval.
    - Chunk size.
    - Number of chunks per pushbuffer.

- **M3. NVLink/RDMA pipeline overlap**
  - Pattern:
    - Copy chunks through CE over NVLink or P2P.
    - Post RDMA reads/writes as soon as the CPU observes chunk completion.
  - Metrics:
    - Pipeline bubble.
    - Effective bandwidth.
    - Overlap ratio.
    - RDMA WR rate.
    - NIC doorbell batch size.

- **M4. RDMA posting pressure**
  - Measure:
    - WR posting throughput.
    - Doorbell batching benefit.
    - Signaled vs unsignaled WR behavior.
    - QP count sensitivity.
  - Motivation:
    - RDMA doorbell batching is a known optimization, but the CE progress bridge creates a new pattern where CE chunk size determines RDMA message rate. ([Kalia et al., ATC 2016](https://www.usenix.org/system/files/conference/atc16/atc16_paper-kalia.pdf))

- **M5. Background compute interference**
  - Compare:
    - SM relay kernel.
    - CUDA API based CE copy.
    - Custom CE progress bridge.
  - Background workload:
    - Persistent GEMM or synthetic compute kernel.
  - Metrics:
    - Compute slowdown.
    - SM occupancy.
    - Copy/RDMA bandwidth.
    - CPU usage.

- **M6. Ordering and data-validity checks**
  - Use deterministic chunk patterns:
    - `chunk_id`
    - sequence number
    - checksum
    - boundary canaries
  - Test:
    - Different chunk sizes.
    - Different GPU/NIC affinity.
    - Same NUMA vs cross NUMA.
    - Same root complex vs less favorable topology, when available.
  - Goal:
    - Validate that semaphore observation implies RDMA-safe data visibility for the tested platform.

### 10.2 Application-motivated controlled workloads

- **A1. Broadcast collective pattern**
  - Controlled pattern:
    - One GPU owns the source buffer.
    - CE copies data to peer GPUs inside the node.
    - RDMA transfers completed chunks to remote node(s), or receives remote data and fans out locally.
  - Baselines:
    - MPI / host-mediated broadcast.
    - NCCL broadcast.
    - NCCL GIN if available.
    - CUDA Runtime API based CE shim.
    - SM relay shim.
  - Metrics:
    - Bandwidth.
    - Latency.
    - SM usage.
    - CPU usage.
    - Progress granularity.

- **A2. MoE dispatch with token deduplication**
  - Controlled pattern:
    - Remote tokens are deduplicated by destination node.
    - One local GPU receives or prepares token chunks.
    - CE/NVLink distributes token chunks to local expert GPUs.
  - Example:

```text
remote tokens
    |
    | RDMA
    v
  GPU0
    |
    | CE / NVLink fanout
    v
  GPU1, GPU2, GPU3
```

  - Data sources:
    - Synthetic routing distributions.
    - Trace-like token distributions collected from MoE inference/training scripts, if available.
  - Baselines:
    - DeepEP-style SM relay.
    - CUDA Runtime API based CE copy.
    - Custom CE progress bridge.
  - Metrics:
    - Dispatch bandwidth.
    - Time-to-first-completed-chunk.
    - SM interference with expert compute.
    - CPU polling/posting overhead.
    - Effect of token skew.

- **A3. NIC-affinity relay**
  - Controlled pattern:
    - Source GPU has poor direct affinity to the NIC.
    - CE first moves data over NVLink to a NIC-affine GPU.
    - RDMA then sends data through the local NIC.

```text
Unoptimized path:

  GPU1 --PCIe--> NUMA1 --UPI/QPI--> NUMA0 --PCIe--> NIC0

CE-progress relay:

  GPU1 --NVLink/CE--> GPU0 --PCIe/GPUDirect RDMA--> NIC0
```

  - Baselines:
    - Direct GPUDirect RDMA from poorly affiliated GPU.
    - NCCL PXN-like topology-aware relay where applicable.
    - SM relay kernel.
    - CUDA Runtime API based CE copy.
  - Metrics:
    - Effective bandwidth.
    - Relay latency.
    - CPU cost.
    - SM interference.
    - Sensitivity to chunk size and doorbell batching.

## 12. Related Work

- **Topology-aware GPU/NIC communication**
  - **NCCL PXN, 2022**: routes GPU traffic through NVLink to reach better NIC paths and rail-optimized topologies. This work motivates the value of NVLink/RDMA bridging but does not expose fine-grained Copy Engine progress as a primitive. ([NVIDIA Developer Blog, 2022](https://developer.nvidia.com/blog/doubling-all2all-performance-with-nvidia-collective-communication-library-2-12/))
  - **FuseLink, 2025**: uses intra-server links and GPU relay to utilize multiple NICs under imbalanced traffic, showing the importance of dynamic GPU/NIC traffic steering. Our current proposal does not evaluate multi-rail aggregation because the testbed is insufficient. ([FuseLink, OSDI 2025](https://www.usenix.org/conference/osdi25/presentation/ren))

- **MoE and expert-parallel communication**
  - **DeepEP, 2025**: provides high-performance MoE dispatch/combine kernels and targets zero or minimal SM occupation. Azure’s DeepEP discussion highlights asymmetric NVLink/RDMA forwarding and 20-SM saturation for the forwarding kernels. ([DeepEP GitHub, 2025](https://github.com/deepseek-ai/DeepEP))
  - **FEPLB, 2026**: uses NVLink Copy Engines for SM-free intra-node MoE load balancing. It is closest in spirit to Copy Engine based MoE movement, but it focuses on intra-node redistribution and load balancing rather than fine-grained CE progress for RDMA pipelining. ([FEPLB, arXiv 2026](https://arxiv.org/html/2604.19654v1))

- **GPU-initiated networking**
  - **NVSHMEM / IBGDA, 2022**: removes the CPU from the internode communication control path by letting GPU SMs interact directly with the NIC, improving fine-grained communication throughput. This validates the cost of CPU proxy paths but uses SMs for NIC control. ([NVIDIA Developer Blog, 2022](https://developer.nvidia.com/blog/improving-network-performance-of-hpc-systems-using-nvidia-magnum-io-nvshmem-and-gpudirect-async/))
  - **NCCL GIN, 2025**: integrates GPU-initiated network primitives into NCCL, with GDAKI for direct GPU-to-NIC communication and Proxy for CPU-assisted operation. Our approach differs by using Copy Engine progress, not SM-issued network operations, as the trigger for RDMA scheduling. ([NCCL GIN, arXiv 2025](https://arxiv.org/html/2511.15076v2))

- **Copy Engine collectives**
  - **NCCL CE Collectives, 2025**: offload certain NVLink-domain collectives to Copy Engines and reduce SM contention. Our proposal targets the missing inter-domain progress bridge between CE movement and RDMA scheduling. ([NVIDIA Developer Blog, 2025](https://developer.nvidia.com/blog/fusing-communication-and-compute-with-new-device-api-and-copy-engine-collectives-in-nvidia-nccl-2-28/))

- **CUDA batching and launch overhead**
  - **CUDA Graphs, 2019–2024**: reduce CPU overhead by batching GPU operations into reusable graph launches, but do not directly provide per-chunk CE progress for streaming RDMA. ([NVIDIA CUDA Graphs Blog, 2019](https://developer.nvidia.com/blog/cuda-graphs/))
  - **`cudaMemcpyBatchAsync`, 2025**: batches multiple memory copies, but public documentation exposes batch-level ordering semantics and explicitly says copies within a batch have no ordering guarantee. ([CUDA Toolkit 12.8 Release Notes](https://docs.nvidia.com/cuda/archive/12.8.2/cuda-toolkit-release-notes/index.html))

- **RDMA posting and doorbell batching**
  - **Kalia et al., 2016**: characterize high-performance RDMA design and describe doorbell batching as a way to reduce CPU-generated MMIO and PCIe transactions. Our proposal borrows this batching mindset but applies it to the GPU Copy Engine command-submission side as well. ([Kalia et al., ATC 2016](https://www.usenix.org/system/files/conference/atc16/atc16_paper-kalia.pdf))

- **GPU command-stream reverse engineering**
  - **Demystifying NVIDIA GPU Internals, 2024**: identifies channels, runlists, engines, and Copy Engine scheduling behavior as key hidden GPU internals. ([Demystifying NVIDIA GPU Internals, RTAS 2024](https://www.cs.unc.edu/~jbakita/rtas24.pdf))
  - **Revealing NVIDIA Closed-Source Driver Command Streams, 2026**: reconstructs the path from pushbuffer construction to GPFIFO enqueue and GPU doorbell notification, and shows that customized commands can be emitted after identifying pushbuffer and semaphore structures. ([Revealing NVIDIA Closed-Source Driver Command Streams, arXiv 2026](https://arxiv.org/html/2604.26889v1))
  - **`cuda_ioctl_sniffer`**: demonstrates practical CUDA ioctl and command-submission exploration, including launching CUDA work without the normal CUDA driver runtime path. ([cuda_ioctl_sniffer GitHub](https://github.com/geohot/cuda_ioctl_sniffer))

## 13. Summary of the Proposal

- This project investigates whether **fine-grained Copy Engine progress** can serve as a practical bridge between intra-node NVLink movement and inter-node RDMA movement.

- The design:
  - Reprograms Copy Engine pushbuffers.
  - Inserts per-chunk release fences and semaphore updates.
  - Lets the CPU observe chunk-level Copy Engine progress.
  - Uses RDMA doorbell batching to transmit completed chunks.
  - Avoids SM relay kernels in the data movement path.

- The main technical bet:
  - Public CUDA APIs can batch Copy Engine work, but they do not expose the progress granularity needed for NVLink/RDMA pipelining.
  - A restricted CE shim can preserve batching while exposing per-chunk progress.
  - If CPU polling and RDMA posting can be amortized with proper chunk sizing and doorbell batching, the design can reduce SM interference while preserving high overlap between NVLink and RDMA transfers.
