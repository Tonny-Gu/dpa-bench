# Bridging NVLink and RDMA with Copy-Engine–Driven Pipelined Communication

## Introduction

- Modern distributed GPU systems are built on two high-performance communication domains:
  - **Intra-node GPU fabrics**, such as NVLink / NVSwitch, for high-bandwidth GPU-to-GPU transfers inside a server.
  - **Inter-node RDMA networks**, such as InfiniBand or RoCE, for low-latency communication across servers.

- These two domains are increasingly used together:
  - **NCCL，2017**，ring Broadcast和AllGather就可能存在同一数据在ring上跨domain传输的情况。
  - **NCCL PXN, 2022** uses NVLink to route GPU traffic toward better-affined NICs and rail-optimized paths. [[NVIDIA PXN blog, 2022](https://developer.nvidia.com/blog/doubling-all2all-performance-with-nvidia-collective-communication-library-2-12/)]
  - **DeepEP, 2025** targets high-throughput and low-latency MoE dispatch/combine, where tokens may move across nodes through RDMA and then be redistributed inside a node. [[DeepEP GitHub](https://github.com/deepseek-ai/DeepEP)]
  - **FuseLink, 2025** uses intra-server GPU links and relay GPUs to utilize multiple NICs for inter-server GPU communication. [[FuseLink, OSDI 2025](https://www.usenix.org/conference/osdi25/presentation/ren)]

- 然而目前这些工作往往使用suboptimal的**SM-mediated forwarding**的方法bridge两个domain。这种方法需要在通讯过程中，在GPU的SM单元上运行一个communication kernel。这个kernel会把large transfer切成很多chunk来pipeline NVLink和RDMA的传输。
- 这个kernel需要占用GPU珍贵的计算资源，常常与background的计算kernel产生干扰，同时communication kernel需要的实时性也增大了runtime调度kernel的难度。
- 但是GPU上有一个存在了很久的DMA-like的单元，名为Copy Engine（CE）。它用于Host与GPU以及GPU之间通过PCIe或者NVLink的异步数据传输，同时不占用SM计算资源。
- 因此，This proposal is based on a simple but powerful idea: 用Copy Engine来bridge NVLink和RDMA的chunk传输。
- 使用Copy Engine进行SM-free的intra-node communication已有先例，NCCL 2.28 introduced Copy Engine based collectives:
  - 它的提出正是为了消除传统的NCCL的communication kernel造成的SM resource contention问题。
  - 同时因为没有kernel，消除了kernel launch overhead，使得NCCL-CE有更好的延迟表现。
- 然而NCCL-CE并不支持inter-node communication，Copy Engine是直接进行整个数据传输而不是chunk粒度的传输。

- 上面的表给出了两个A100在NVLink下使用`cudaMemcpyAsync`和`cudaMemcpyBatchAsync`调用Copy Engine复制各种size的chunk的性能。
- 这个proposal希望实现CE-based fowarding。然而我们发现最大的问题是CE在拷贝KB级别尺寸的chunk时性能不佳，特别是4-7KB这个尺寸，这是MoE模型中一个token的典型的hidden size。假设我们使用400G网络，那么4-7KB数据的传输时间在0.1us这个量级，因此任何亚微秒级的overhead都不能忽视。
- 我们深入研究发现，当前CUDA API并没有做很多亚微秒级别的优化。在这个尺度下，我们认为work submission和保证memory order和visibility带来的overhead远超出了真正数据的传输时间。
- 此外CE-based forwarding需要fine-grained completion signal，如果使用当前CUDA API实现，也会有不小的overhead。

- 但我们发现Copy Engine存在的灵活性和一些hardware capabilities可以让我们做进一步的优化，但它们没有被公开API暴露出来和利用。
- 因此To this end, we propose a lightweight shim layer that enables direct control over Copy Engine command streams，具体来说这个shim layer构建了绕过CUDA runtime的work submission path并直接low-level的Copy Engine的command来控制Copy Engine, 这让我们得以实现batched submission，hardware-native progress signaling，memory fence coalescing，以及low-latency submission path。

- We plan to evaluate this design through microbenchmarks and application-level experiments, 对于application，我们计划实现SM-free的Broadcast和MoE-style dispatch collectives. microbenchmarks的Baselines will include CUDA公开API实现的CE-based forwarding和SM-mediated forwarding，application-level的baseline是existing communication libraries such as NCCL，NCCL-CE以及DeepEP.

- In summary, this work 挖掘和展示了GPU Copy Engine的potential, elevating it from a 大块数据的 data mover to a pipelined cross-domain communication engine. By doing so, it enables a new class of pipelined communication mechanisms that better exploit the capabilities of modern GPU systems.

## Background

### Copy Engine，Compute Engine和TMA

- 参考https://www.cs.unc.edu/~jbakita/rtas24.pdf的Fig2画一个GPU架构图
- GPU上实际上有三个东西都可以完成数据搬运：Copy Engine，Compute Engine和TMA
- 本文用SM指代Compute Engine， CE指Copy Engine，local指当前GPU，peer指同一node的GPU，remote指其他node的GPU
- 简单介绍一下Compute Engine，Copy Engine和TMA
  - Copy Engine是一个自CUDA诞生初期就存在在GPU上的DMA-like外设，它由CPU控制，负责Host Memory与GPU的Global Memory （GMEM）之间的数据搬运，独立于SM并辅助SM
  - Compute Engine是GPU的主要部分，执行GPU kernel的单位，GPU kernel是指可以运行在Compute Engine / Streaming Multiprocessor （SM）的GPU程序
    - SM的kernel可以用load store指令访问内存
  - 然后TMA是从Hopper开始引入的由SM控制的DMA-like单元，实际上是SM的一部分，本来的用途是让SM用更少的指令完成GMEM与SM的Shared Memory（SMEM）之间的数据搬运，以饱和Tensor Core的吞吐。Ampere GPU上的`cp.async`是TMA的前身，功能类似。
- 然后有两项成对的技术极大的扩展了GPU的访存范围：GPUDirect P2P和Unified Virtual Addressing （UVA）
  - 这两项技术早于NVLink出现
  - UVA将local GMEM，peer GMEM和host memory放在了统一GPU虚拟地址空间
  - GPUDirect P2P允许local GPU通过PCIe BAR读写peer GPU的GMEM，后来也支持NVLink和NVSwitch
  - 这两项技术的配合，使得CE，SM和TMA直接访问peer GPU的GMEM和host memory（DeepEP；DAK，https://arxiv.org/html/2604.26074v1）

  - ｜ Copy Engine ｜ CPU ｜Local GMEM <-> Host Mem / Peer GMEM ｜
  - ｜ Vanilla Copy Kernel ｜ GPU SM ｜ Local GMEM / Peer GMEM / Host Mem / SM SMEM <-> SM Reg |
  - ｜ Copy Kernel + TMA ｜ GPU SM ｜ Local GMEM / Peer GMEM / Host Mem <-> SM SMEM |

### Modern GPU communication paths

- 画一个表
  - ｜ 方法 ｜ 发起者（控制面） ｜ 执行者（数据面） ｜ 支持的数据路径 | 传输层 ｜
  - ｜ GPUDirect P2P | CPU ｜ Copy Engine ｜ Local GMEM <-> Peer GMEM | PCIe / NVLink / NVSwitch ｜
  - | GPUDirect P2P | GPU SM | GPU SM / TMA | Local GMEM <-> SM Reg / SM SMEM (TMA) <-> Peer GMEM | 同上 |
  - ｜ GPUDirect RDMA（GDR） | CPU | RDMA NIC | Local GMEM <-> Remote Host Mem / GMEM | PCIe + RDMA |
  - | GPUDirect Async (GDAKI) | GPU SM | RDMA NIC | Local GMEM <-> Remote Host Mem / GMEM | PCIe + RDMA |
- 之前介绍的GPUDirect P2P用于intra-node communication
- 而高性能系统中常用RDMA进行inter-node communication。RDMA最早用于让CPU访问Remote Host Memory。
- GPUDirect RDMA （GDR）是一项允许RDMA NIC通过PCIe BAR直接读写GPU的GMEM的技术，可以视为NIC和GPU在做P2P通信，但RDMA操作仍然需要CPU来发起，即CPU负责ring RDMA NIC的doorbell。这项技术在通用的GPU通信库广泛使用，如NCCL，CUDA-aware MPI。
- 而GPUDirect Async Kernel-Initiated（GDAKI），也叫IBGDA，进一步允许GPU SM直接发起RDMA的操作，即RDMA write/send/recv的操作都不需要CPU的帮助，因此也被认为这种技术有延迟优势，在MoE通信库中广泛使用，如DeepEP，Hybrid-EP，NCCL-EP，以及被PGAS风格的通信库的支持，如NVSHMEM和NCCL-GIN。
- 但还有一种叫CPU-assisted IBGDA的fallback，它实际上是GPU SM通过一个Command FIFO向CPU发送命令，然后CPU代为发起GDR的RDMA操作。这种workaround在NCCL，MSCCL，UCCL等工作里广泛使用，为了不与CPU-assisted IBGDA混淆，我们统称这种由GPU-initiated的workaround为CPU-proxied GDR，常规的IBGDA就叫GDAKI。

### SM-mediated forwarding

- 在上个章节介绍的所有工作都采用了SM-mediated forwarding的方法
- 这种方法会在GPU上运行一个communication kernels来转发RDMA和NVLink的数据。
  - 具体来说，这些kernel实现了多级流水
  - 首先decompose large transfers into small chunks
    - 这些chunks的size从数KB到数MB
  - 图里给出了一种N2R的简单实现的例子，使用TMA+GDAKI
  - 第一级流水：TMA load <chunk i @ peer GMEM> to SMEM，这里发生了NVLink的传输
  - 第二级流水：TMA store <chunk i @ SMEM> to GMEM，这里的GMEM是提前注册的通信buffer，即PCIe BAR mapped的锁页内存。
  - 第三级流水：RDMA send <chunk i @ local GMEM> to remote GMEM
  - 在这个流水线中，GPU SM负责发起chunk的TMA和RDMA传输，以及在chunk传输完成后做出反应。

## Challenges

### （帮我想想标题）

- 在上一个章节中我们介绍了SM-mediated forwarding，而我们希望实现CE-based forwarding，即用Copy Engine代替TMA在NVLink传输数据，然后用CPU代替GPU SM完成调度工作
- 在上面的图中我们也可以看到在pipeline NVLink和RDMA的传输时，对每个chunk发起NVLink和RDMA传输的overhead要足够小才可以充分利用RDMA和NVLink的带宽
- 微秒级别的开销是不可忽视的，在400G网络中，每1微秒理论上可以传输50KB的数据了，而MoE模型中，每个token的尺寸也就在7KB左右。
- 我们总结了overhead可能的来源
  - 执行者这里指NVLink上进行copy的单元，发起者指让执行者和RDMA NIC发起传输的单元
  - O1. Work submission：发起者给执行者下命令发起传输本身可能有overhead。
  - O2. Fine-grained completion signal：在做异步拷贝的时候，发起者需要知道执行者的**per-chunk progress**。比如每完成一个chunk在NVLink上的拷贝，就能通知RDMA操作的发起者，让它发起RDMA send/write。但执行者通知发起者可能也有overhead。
  - O3. Cross-domain memory ordering and visibility：比如对于N2R，在发起RDMA send/write的时刻，执行者已经把remote GMEM的chunk通过NVLink拷贝到local GMEM的通信buffer，并且新数据对RDMA NIC完整且可见，保证RDMA NIC不会读取到stale or partially written data。对于R2N，执行者准备将local GMEM上的chunk拷贝到remote GMEM时，RDMA NIC写入local GMEM的数据对执行者完整且可见。然而保证各个domain内的order和跨domain的order往往需要依靠各种级别的memory fence，然而memory fence本身是有overhead的，比如SM的执行system scope fence会消耗上百到上千个cycle。
- 我们回到TMA+GDAKI的SM-mediated forwarding方法看看它的overhead，此时发起者是SM，执行者是TMA
  - 对于O1，TMA紧耦合在SM里，SM发起TMA操作的延迟是在纳秒级别。
  - 对于O2，TMA本来就是一个给GEMM准备的tile wise的DMA-like单元，天然支持Fine-grained completion signal。因为与TMA紧耦合，SM拿到通知的开销也极小。
  - 对于O3，NVLink和RDMA的consumer producer之间靠gpu到system scope的release acquire memory fence保证Cross-domain memory ordering and visibility，但SM上驻留的大量的线程可以掩盖内存操作的延迟。
- 然而对于CE-based forwarding，发起者是CPU，执行者是Copy Engine，
  - 对于O1，使用CPU给位于GPU的Copy Engine提交一次work，和launch kernel一样属于work submission，开销是在亚微秒到微秒级别。而CUDA API中能减少CE的work submission overhead的手段也非常有限。
  - 对于O2，我们发现公开的CUDA API能够获得fine-grained completion signal的方法非常有限，有公开API可以请求record async work完成，开销也是在亚微秒级。
  - 对于O3，根据GDR的官方文档，CUDA work submission APIs provide memory ordering of GDR operations，因此Copy Engine的CUDA API应当能保证Cross-domain memory ordering and visibility。但我们观察到这个memory order的保证很可能不是免费的，然而这个overhead并没有被系统的研究过。

### CUDA API的限制

- 在上个章节我们指出了，Copy Engine的Public API在暴露fine-grained completion signal和减小Command submission overhead存在限制
- CUDA异步编程的模型是，CUDA Stream是一个work queue，CPU每次launch kernel或者copy，都是向CUDA Stream提交一个异步的work，同一Stream内的work会按提交顺序执行
  - 比如我们可以调用`cudaMemcpyAsync`提交一个复制一个chunk的work，或者`cudaMemcpyBatchAsync`提交一个复制多个chunk的work。
  - 然后我们可以调用`cudaEventRecord`提交一个record event的work，CPU可以通过调用`cudaEventQuery`，非阻塞式的检查这个work有没有被GPU执行，也就是说检查CUDA Stream有没有进行到`cudaEventRecord`这个位置，或者`cudaEventSynchronize`让阻塞CPU直到record event的work完成
  - 很自然，对于N2R，我们会写出这样一个trival程序

```py
# work submission
progress = {}
for i in (0, num_chunks):
  progress.append(cudaEventCreate())
for i in (0, num_chunks):
  cudaMemcpyAsync(dst=local_gmem[i], src=peer_gmem[i], kind=P2P, size=chunk_size)
  cudaEventRecord(progress[i])
# 流式发送
start = 0
while start < num_chunks:
  end = start
  while cudaEventQuery(end) == COMPLETE:
    end += 1
  if end > start:
    postRdmaWriteBatch(dst=remote_gmem[start:end], src=local_gmem[start:end], size=chunk_size)
    start = end
```

- 但是这个写法存在问题
  - 我们发现每一次`cudaMemcpyAsync`，`cudaEventRecord`都会产生一个亚微秒级的work submission overhead。这个overhead我们推测主要是CPU和GPU在PCIe上进行多轮round trip的通信导致的，因为PCIe一次单向通信就是亚微秒级。我们会在后面的章节介绍CPU向GPU提交work的submission protocol。
- 这个work submission overhead是GPU一个很知名的问题，目前常用的缓解这个overhead的手段包括
  - `cudaMemcpyBatchAsync`，2025年引入了这个API，并且NCCL-CE正是使用了这个API实现了CE-based collectives。它对于我们的N2R来说，可以一次性提交复制多个chunks的work，并且只产生一次submission overhead，因此在之前的表里我们能看到这个API在小尺寸传输上比`cudaMemcpyAsync`能快一个数量级。但是由于这个方法使用CUDA Event只能拿到整体完成的信号，并不能获得每个chunk copy完成的信号，因此并不适用于我们的N2R程序。
  - CUDA Graph：提前录制所有work submission操作，再instantiate Graph以后，每次replay这个Graph都只产生一次submission overhead。但是record和instantiate这两个操作本身都产生几十微秒的overhead，并且随着node数量变多这个overhead还会增加（https://developer.nvidia.com/blog/constant-time-launch-for-straight-line-cuda-graphs-and-other-performance-enhancements/）。因此也不适合N2R这种不需要多次replay的场景。
  - Persistent Kernel / Mega Kernel：这是通过把很多小kernel fuse成一个大kernel在SM上运行，避免小kernel之间的launch overhead （submission overhead），所以SM-mediated forwarding的Kernel一般都是Persistent的。但这是一个优化SM的submission overhead的方法，并不适用于Copy Engine。

- 对于R2N，我们会写

```py
start = 0
while start < num_chunks:
  num_cqe = pollRdmaCq()
  if num_cqe > 0:
    end = start + num_cqe
    cudaMemcpyBatchAsync(dst=peer_gmem[start:end], src=local_gmem[start:end], size=chunk_size)
    start = end
```
- 我们发现`cudaMemcpyBatchAsync`内部会让Copy Engine做release memory fence，由于我们不需要每次把chunk通过NVLink复制到peer GPU上就要让peer GPU可见，因此我们可以考虑去掉per chunk的release memory fence，defer到传输完成再做一次fence。

- 因此我们需要更细粒度的方法来优化我们的CE-based forwarding。我们从深入`cudaMemcpyBatchAsync`，`cudaMemcpyAsync`和`cudaEventRecord`这三个API，发现了更多的优化机会。

  - 之后work submission会像RDMA NIC一样，往channel里填入command（类似于RDMA NIC往send queue （SQ）写work queue element），然后写入GPU MMIO来ring doorbell，bypass kernel
  - 由于CUDA Runtime和CUDA Driver的职能大部分重叠，之后提到把CUDA Runtime和CUDA Driver统一用CUDA Runtime指代，来和Kernel Module做出区分

### Work Submission Path

- 介绍一下GPU channel
  - CUDA Runtime向GPU提交任务用的一个ring buffer结构
  - 在CUDA Runtime中，每个channel负责提交一种Engine，比如Compute Engine或者Copy Engine的command
  - command是GPU上各种Engine原生支持的一种low-level primitive。CUDA Runtime提交的work在执行时会lower成一串command。
  - 具体来说channel是两级结构，第一级是叫GPFIFO的ring buffer，第二级是Push Buffer，是一块线性内存区
    - Each GPFIFO entry points to a push buffer.
    - Each push buffer contains a sequence of low-level GPU commands，长度不固定.
  - 一般来说Push Buffer要比GPFIFO大得多
  - Push Buffer内的command会按顺序执行。GPFIFO也是顺序执行的，一个接一个的执行Push Buffer里的command。
  - 采用这种结构可能是为了在图形栈中重用Push Buffer里的command来减少生成command的开销（如OpenGL的`GL_NV_command_list`扩展），以及允许多CPU线程同时生成Push Buffer command，但我们在CUDA中并没有观察到Push Buffer里的command被重复使用。
  - 我们观察到在CUDA中GPFIFO位于GMEM上，也有人观察到Vulkan的GPFIFO位于Host Memory。而在CUDA中Push Buffer在Host Memory上。
- CPU提交work的过程是
  1. Write pushbuffer commands.
  2. Fill one GPFIFO entry pointing to the pushbuffer segment.
  3. Advance GP_PUT （producer index, points to the oldest unconsumed entry）.
  4. Ring GPU doorbell through MMIO write.
- 然后GPU上有个PBDMA（不同于TMA和Copy Engine），负责把channel里的数据DMA read到GPU上
  5. Fetch GP_PUT / channel state.
  6. Fetch GPFIFO entry.
  7. Fetch pushbuffer command stream.
  8. Parse commands and dispatch them to Compute / Copy Engine.
- 我们可以发现从CPU发出doorbell开始，到Copy Engine开始工作之间，latency至少有1.5个PCIe的RTT（大概在微秒级），其中Host更新GPFIFO和ring doorbell消耗0.5RTT，然后PBDMA read PushBuffer command要1个RTT，假设PBDMA read GMEM上的GPFIFO不消耗很长的时间。

### CUDA Runtime Internals

- We use并且修改了 `geohot/cuda_ioctl_sniffer` to inspect CUDA Runtime interaction with GPU work submission并研究为什么`cudaMemcpyBatchAsync`显著比`cudaMemcpyAsync`快.

- We inspect this code pattern:

```py
cudaMemcpyAsync(dst=d[0], src=s[0], size=n, kind=P2P, stream=0)
cudaMemcpyBatchAsync(dst=[d[1], d[2]], src=[s[1], s[2]], size=[n, n], kind=P2P, stream=0)
cudaEventRecord(event, stream=0)
```

- 然后我们发现这三次API call大致被展开成这样，下面的例子为了便于理解做了很大的简化，ceLaunchDma和ceReleaseSemaphore这些command实际上每个都是有好几条PushBuffer command组成的`
- 实际上`cudaMemcpy`会根据`kind`和`size`的不同，也可能使用Copy Engine以外的Engine完成。`cudaEventRecord`在不同Engine的channel上也会为不同的Engine生成不同但类似的semaphore相关的command。

```py
# cudaMemcpyAsync(dst=d[0], src=s[0], size=n, kind=P2P)
updateGpFifoEntry(channel=CE, index=2, pbuf_addr=...)
writePbufCommands(pbuf_addr=..., commands=[
  ceLaunchDma(dst=d[0], src=s[0], size=n),
  ceReleaseSemaphore(addr=_stream0_internal_ce, payload=4),
])
ringDoorbell(channel=CE)

# cudaMemcpyBatchAsync(dst=[d[1], d[2]], src=[s[1], s[2]], size=[n, n], kind=P2P, stream=0)
updateGpFifoEntry(channel=CE, index=3, pbuf_addr=...)
writePbufCommands(pbuf_addr=..., commands=[
  ceLaunchDma(dst=d[1], src=s[1], size=n),
  ceLaunchDma(dst=d[2], src=s[2], size=n),
  ceReleaseSemaphore(addr=_stream0_internal_ce, payload=5),
])
ringDoorbell(channel=CE)

# cudaEventRecord(event, stream=0)
updateGpFifoEntry(channel=CE, index=4, pbuf_addr=...)
writePbufCommands(pbuf_addr=..., commands=[
  ceReleaseSemaphore(addr=event, payload=...)
  ceReleaseSemaphore(addr=_stream0_internal_ce, payload=6),
])
ringDoorbell(channel=CE)
```

- 其中
  - 介绍一下updateGpFifoEntry， writePbufCommands， ringDoorbell，ceReleaseSemaphore， ceLaunchDma都是啥，参数都是啥意思
  - 其中ceReleaseSemaphore有Flush Copy Engine DMA的语义，Release这里指release fence，release store semaphore
- 然后我们发现（这些Lession分一下组然后给个L1 L2的编号吧）
  - `cudaMemcpyBatchAsync`的每一对（dst，src）pair都变成了一个`ceLaunchDma`的command。
  - 每一次Copy Engine的`memcpy`和`cudaEventRecord`的API call都会且只会ring一次doorbell。这意味着`cudaMemcpyBatchAsync`比`cudaMemcpyAsync`快原因之一是相当于做了doorbell batching。
    - 在RDMA系统上，doorbell batching是个很广泛使用的提升性能的技巧。([Kalia et al., ATC 2016](https://www.usenix.org/system/files/conference/atc16/atc16_paper-kalia.pdf))
  - 每次Copy Engine `memcpy`做完DMA后都会做一次`ceReleaseSemaphore`来flush DMA和memory fence来保证CUDA work submission APIs provide memory ordering的语义，同时更新semaphore。这意味着`cudaMemcpyBatchAsync`更快的原因之二是它做了更少的memory fence和semaphore写入，每次semaphore写都是一次PCIe write。
  - semaphore实际上是GPU可访问的，储存在host memory上的一个变量，Copy Engine执行`ceReleaseSemaphore`时，会用payload field的立即值更新这个变量，并且这个值的变化对Host（CPU）是可见的
    - 但是`memcpy`写的semaphore对用户是不可见的
    - 这是CUDA Runtime为每个stream和每个channel维护了内部semaphore，我们认为这个semaphore会被用于
      - 用于Host阻塞式等待Stream完成（`cudaStreamSynchronize`）
      - 用于跨channel的同步（因为不同的Engine的work必须通过不同的channel来提交），我们观察到了同一Stream的属于不同Engine的两个work之间插入了等待和acquire semaphore的command
      - 用于倒推出GPFIFO的头指针，来判断GPFIFO是不是满了
  - `cudaEventRecord`的本质是两次semaphore写和两次release memory fence。一个是CUDA Runtime的内部semaphore，一个是用户指定的semaphore。
    - 也就是说每次API call都产生了一次doorbell，两次semaphore，和两次memory fence。
  - semaphore的payload值是command的字面量，但是`cudaEventRecord`并不能指定semaphore的payload，也不能被`cudaEventQuery`读取。
    - 也就是说`ceReleaseSemaphore`这个command可以拿来给我们实现custom的progress signal。
  
- 因此我们可以思考，我们能否构造我们自己的Push buffer command从而同时实现
  - doorbell batching
  - custom progress signaling
  - less memory fence

## Our Solution：Shim Layer

- 之前我们给出了trivial的N2R和R2N的实现
- 我们的shim layer enables direct control over Copy Engine command streams，然后在此基础之上提供了为N2R，R2N，R2N Multicast， 专用的Copy Engine API，`ceBatchCopy`，`ceStreamCopy`。

### N2R

- 我们为N2R准备了`ceBatchCopy`，参考的N2R实现如下
  - 简短介绍一下有什么和trivial N2R区别

```py
# work submission
start = 0
end = 0
ceBatchCopy(dst=local_gmem[:], src=peer_gmem[:], size=chunk_size, ubatch=ubatch, progress_ptr=ptr(end))
# 流式发送 
while start < num_chunks:
  if end > start: # have new completions
    postRdmaWriteBatch(dst=remote_gmem[start:end], src=local_gmem[start:end], size=chunk_size)
    start = end
```

- 然后`ceBatchCopy`实际上underlying在做

```py
updateGpFifoEntry(channel=CE, index=..., pbuf_addr=...)
writePbufCommands(pbuf_addr=..., commands=[
  ceLaunchDma(dst=dst[0], src=src[0], size=size),
  ceLaunchDma(dst=dst[1], src=src[1], size=size),
  ...
  ceLaunchDma(dst=dst[ubatch - 1], src=src[ubatch - 1], size=size),
  ceReleaseSemaphore(addr=progress_ptr, payload=ubatch),

  ceLaunchDma(dst=dst[ubatch], src=src[ubatch], size=size),
  ceLaunchDma(dst=dst[ubatch + 1], src=src[ubatch + 1], size=size),
  ...
  ceLaunchDma(dst=dst[2 * ubatch - 1], src=src[2 * ubatch - 1], size=size),
  ceReleaseSemaphore(addr=progress_ptr, payload=2 * ubatch),

  ...
  ceLaunchDma(dst=dst[num_chunks - 1], src=src[num_chunks - 1], size=size),
  ceReleaseSemaphore(addr=progress_ptr, payload=num_chunks),
])
ringDoorbell(channel=CE)
```

- 对比使用`cudaMemcpyAsync`的trivial N2R实现，我们实现了
  - batch submission：trivial的N2R对每个chunk产生两次work submission，而`ceBatchCopy`总共只产生一次work submission
  - memory fence coalescing：`ceBatchCopy`将组织成microbatch，每microbatch size个chunk更新一次semaphore和做一次memory fence。而trivial的N2R是每个chunk更新三次semaphore和做三次memory fence。
  - hardware-native progress signaling：`ceBatchCopy`利用semaphore的custom payload暴露细粒度的progress，不需要为每个chunk创建一个user semaphore并调用`cudaEventRecord`。

### R2N and R2N Multicast

- 我们为R2N和R2N Multicast准备了`ceStreamCopy`，参考的R2N实现如下
  - 简短介绍一下有什么和trivial R2N区别
- R2N Multicast可以通过在`ceStreamCopy`的`src`和`dst`参数里，一次性指定多个GPU的`dst`地址（这两个参数都是列表，`ceStreamCopy`也有batch语义），比如`dst=[peer1_dst, peer0_dst], src=[local_src, local_src]`

```py
start = 0
while start < num_chunks:
  num_cqe = pollRdmaCq()
  if num_cqe > 0:
    end = start + num_cqe
    eof = True if end == num_chunks - 1 else False
    ceStreamCopy(dst=peer_gmem[start:end], src=local_gmem[start:end], size=chunk_size, eof=eof, progress_ptr=ptr(end))
    start = end
```

- 然后`ceStreamCopy`实际上underlying在做

```py
updateGpFifoEntry(channel=CE, index=..., pbuf_addr=...)
writePbufCommands(pbuf_addr=..., commands=[
  ceLaunchDma(dst=dst[start], src=src[start], size=size),
  ceLaunchDma(dst=dst[start + 1], src=src[start + 1], size=size),
  ceLaunchDma(dst=dst[start + 2], src=src[start + 2], size=size),
  ...
  ceLaunchDma(dst=dst[end], src=src[end], size=size),
  ceReleaseSemaphore(addr=progress_ptr, payload=num_chunks) if eof,
])
ringDoorbell(channel=CE)
```

- 对比使用`cudaBatchMemcpyAsync`的trivial N2R实现，整个过程只在最后产生一次semaphore write和memory fence。

### 实现

- 作为实验性的shim layer，我们沿用`cuda_ioctl_sniffer`的，使用`LD_PRELOAD`劫持ioctl函数的方法，来嗅探和插入CUDA Runtime与Kernel Module之间的指令流。
- ioctl的指令流里包含了channel创建的指令，因此在CUDA Runtime创建channel的时候，我们可以注入指令来创建shim layer专用的channel。
- 在ioctl的指令流里也有请求userspace可写入的GPU doorbell MMIO地址，我们的shim layer可以嗅探出这个地址，这样我们可以使用我们own的channel，不经过CUDA Runtime，直接将command提交给GPU。

## 其他可探索的优化方向

### Relocate Push Buffer到GPU GMEM

- 在之前的章节我们介绍过CUDA的GPFIFO位于GMEM上，Vulkan的GPFIFO位于Host Memory。而CUDA和Vulkan的Push Buffer都Host Memory上。
- 这提示了我们把Push Buffer也移到GMEM上可能是可行的，且有收益的。
- 之前我们分析了一次对Host memory的PBDMA read会在PCIe上产生一次roundtrip，CUDA将GPFIFO挪到GMEM上避免了两次PCIe上的PBDMA read
- 那进一步把Push Buffer移到GMEM上，避免最后一次PBDMA在PCIe上的read，只剩下Host write to GPFIFO和Push Buffer的到GPU GMEM的单程PCIe通信，会有多大的性能收益？

### 同方向多Copy Engine

- 目前CUDA Runtime限制每个方向比如H2D，D2H，P2P上同时只能有一个运行的Copy Engine，因为一般认为一个Copy Engine足够饱和链路带宽，因此并没有必要在同一个链路上用多个Copy Engine
- Copy Engine在chunk size很小的时候，是用不满链路带宽的。
- 因此说不定在同一链路上同时使用多个Copy Engine可以提升带宽利用率。

## Evaluation Plan

- Microbenchmarks:
  - CE-based fowarding在N2R和R2N场景下的copy latency and bandwidth over NVLink.
  - GPU doorbell latency and amortized cost versus batch size.
  - RDMA doorbell latency and amortized cost versus WQE list size.
  - End-to-end overlap efficiency between Copy Engine transfers and RDMA writes.
  - SM occupancy, achieved compute throughput, and interference under background GEMM.
- Baselines:
  - CE-based fowarding 只用标准CUDA APIs.
  - SM-mediated forwarding modeled after GPU communication kernels used in systems such as DeepEP and NCCL GIN.
  - Existing collectives and communication libraries, including MPI, NCCL, NCCL-CE, and DeepEP.
- Application 1: Broadcast collective.
  - Root GPU receives or owns the broadcast buffer.
  - Copy Engine replicates the buffer to local GPUs over NVLink.
  - RDMA sends chunks to remote nodes as soon as the relevant local copy chunks complete.
- Application 2: Expert-parallel dispatch.
  - Deduplicate tokens that arrive once over RDMA but are needed by multiple local GPUs.
  - Use Copy Engine replication instead of an SM copy kernel.
  - Evaluate with synthetic token distributions and traces collected from MoE inference.

## Related Work

### Topology-aware GPU/NIC communication

- **NCCL PXN, 2022**
  - Uses NVLink plus PCIe to let GPUs reach better NIC paths and rail-optimized network paths.
  - Closest motivation for NIC-affinity relay.
  - Difference: PXN is NCCL-internal, while this proposal studies an explicit Copy Engine based bridge for chunked RDMA overlap. [[NVIDIA PXN blog, 2022](https://developer.nvidia.com/blog/doubling-all2all-performance-with-nvidia-collective-communication-library-2-12/)]

- **FuseLink, 2025**
  - Uses intra-server GPU links and relay GPUs to improve multi-NIC utilization.
  - Difference: this proposal does not evaluate multi-rail aggregation in the first testbed; it targets Copy Engine relay. [[FuseLink, OSDI 2025](https://www.usenix.org/conference/osdi25/presentation/ren)]

### MoE and expert-parallel communication

- **DeepEP, 2025**
  - Provides MoE dispatch/combine GPU kernels and targets zero or minimal SM occupation.
  - Difference: this proposal specifically studies Copy Engine based intra-node relay and CE-to-RDMA pipelining. [[DeepEP GitHub](https://github.com/deepseek-ai/DeepEP)]

### Copy Engine based communication

- **NCCL CE Collectives, 2025**
  - Uses Copy Engines to drive NVLink transfers and reduce SM contention for selected data-movement collectives.
  - Difference: NCCL CE collectives focus on NVLink-domain collectives; this proposal uses Copy Engines to bridge NVLink-domain movement with RDMA-domain movement. [[NVIDIA NCCL 2.28 blog, 2025](https://developer.nvidia.com/blog/fusing-communication-and-compute-with-new-device-api-and-copy-engine-collectives-in-nvidia-nccl-2-28/)]

### GPU-initiated networking

- **NCCL GIN / Device API, 2025**
  - Lets GPU code participate directly in network operations through NCCL Device API.
  - Difference: GIN is a GPU-initiated networking path; this proposal keeps Copy Engine as the relay engine and uses CPU-assisted RDMA posting in the first prototype. [[NVIDIA NCCL 2.28 blog, 2025](https://developer.nvidia.com/blog/fusing-communication-and-compute-with-new-device-api-and-copy-engine-collectives-in-nvidia-nccl-2-28/)]

### CUDA batching and runtime APIs

- **CUDA Graphs, 2019–2024**
  - Batch GPU work into graphs and reduce repeated launch overhead.
  - Difference: CUDA Graphs do not expose ordered per-chunk CE completion inside a streaming copy batch. [[NVIDIA CUDA Graphs blog](https://developer.nvidia.com/blog/cuda-graphs/)]

- **`cudaMemcpyBatchAsync`, 2025**
  - Supports batched memory copies, but public documentation says copies inside a batch have no specific ordering guarantee.
  - Difference: this proposal needs ordered per-chunk CE release inside the command stream. [[CUDA runtime documentation](https://nvidia.github.io/cuda-python/cuda-bindings/latest/module/runtime.html)]

### RDMA doorbell batching

- **Kalia et al., 2016**
  - Characterizes RDMA optimizations such as doorbell batching, BlueFlame, and reducing CPU-generated MMIOs.
  - Difference: this proposal applies the batching lesson to the GPU Copy Engine submission path, where PBDMA, GPFIFO, and pushbuffer fetching make unbatched GPU doorbells unattractive. [[Kalia et al., ATC 2016](https://www.usenix.org/system/files/conference/atc16/atc16_paper-kalia.pdf)]

### GPU command-stream reverse engineering

- **Demystifying NVIDIA GPU Internals, 2024**
  - Studies NVIDIA GPU engines, channels, runlists, and Copy Engine behavior.
  - Relevance: provides the hardware mental model for CE as an independent data-movement engine. [[Demystifying NVIDIA GPU Internals, RTAS 2024](https://www.cs.unc.edu/~jbakita/rtas24.pdf)]

- **Revealing NVIDIA Closed-Source Driver Command Streams, 2026**
  - Reconstructs pushbuffer, GPFIFO, USERD, PBDMA, and doorbell behavior.
  - Relevance: directly supports the feasibility of custom CE command-stream construction. [[Revealing NVIDIA Closed-Source Driver Command Streams, 2026](https://arxiv.org/html/2604.26889v1)]

- **`cuda_ioctl_sniffer`**
  - Demonstrates practical CUDA ioctl and command-queue exploration.
  - Relevance: provides a starting point for understanding and experimenting with CUDA-less command submission. [[cuda_ioctl_sniffer](https://github.com/geohot/cuda_ioctl_sniffer)]
