# Bridging Intra-node and Inter-node GPU Networks with Reprogrammed Copy Engines

## Abstract

- Modern GPU clusters now contain two high-performance but weakly integrated communication domains:
  - Intra-node GPU fabrics, such as NVLink and NVSwitch, optimized for GPU-to-GPU movement inside one server or rack-scale NVLink domain.
  - Inter-node RDMA fabrics, such as InfiniBand and RoCE, optimized for low-latency data movement across servers.
- Existing systems increasingly bridge these domains by routing RDMA traffic through GPUs and then moving data over NVLink, or vice versa.
- The dominant implementation strategy uses GPU SMs to execute forwarding kernels, which consumes compute resources and can interfere with colocated model computation.
- This proposal explores a different design point: reprogramming GPU Copy Engines to bridge NVLink and RDMA traffic without occupying SMs.
- The core idea is to expose fine-grained Copy Engine progress to the host or network stack, so that each completed NVLink chunk can immediately trigger an RDMA operation.

## Motivation

- GPU clusters evolved from single-GPU accelerators into dense multi-GPU nodes connected by high-bandwidth intra-node fabrics.
  - NVIDIA documents NVLink as a high-bandwidth GPU interconnect for scale-up communication: <https://www.nvidia.com/en-us/data-center/nvlink/>.
  - NCCL is topology-aware and supports PCIe, NVLink, Ethernet, and InfiniBand collectives: <https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/overview.html>.
- RDMA evolved earlier than today's GPGPU-centric systems and was designed around queue pairs, memory registration, and NIC-driven DMA rather than GPU fabric semantics.
  - GPUDirect RDMA exposes a direct path between GPUs and third-party PCIe devices such as NICs, but it still has topology constraints, memory-ordering caveats, BAR-space limits, and driver integration requirements: <https://docs.nvidia.com/cuda/gpudirect-rdma/>.
  - The GPUDirect RDMA documentation explicitly notes that the best case is a GPU and third-party device under PCIe switches, while paths through CPU/IOH or QPI/HT can be slower or unreliable: <https://docs.nvidia.com/cuda/gpudirect-rdma/#supported-systems>.
  - Cache-coherent PCIe through CXL is a promising direction, but broad production deployment is still in progress: <https://www.computeexpresslink.org/>.
- The boundary between NVLink and RDMA is therefore a real systems bottleneck.
  - RDMA and GPU fabric APIs expose different completion semantics.
  - Cross-vendor and cross-device interoperability remains difficult.
  - CPU NUMA topology, PCIe root complexes, and NIC affinity can dominate the actual data path.
- Recent systems already exploit GPUs as relay points between the two domains.

## Existing GPU Relay Patterns

- NCCL PXN uses NVLink plus PCIe to reach a better NIC when GPU-to-NIC affinity is poor.
  - PXN is described in the NVIDIA NCCL 2.12 blog: <https://developer.nvidia.com/blog/doubling-all2all-performance-with-nvidia-collective-communication-library-2-12/>.
  - Example: avoiding a cross-socket CPU path.

```text
Before PXN:

  GPU1 --PCIe--> NUMA1 --UPI/QPI--> NUMA0 --PCIe--> NIC0

After PXN:

  GPU1 --NVLink--> GPU0 --PCIe--> NIC0
```

- NCCL PXN also performs rail-aware routing to reduce spine-switch traffic.
  - PXN assumes a rail-optimized topology where NIC y on every node connects to Leaf y.
  - It first moves data to the GPU close to the rail-matched NIC, then sends through that NIC.

```text
Before PXN rail optimization:

  Node0 GPU0
      |
  Node0 NIC0 -- Leaf0 -- Spine -- Leaf3 -- Node1 NIC3 -- Node1 GPU3

After PXN rail optimization:

  Node0 GPU0 -- NVSwitch -- Node0 GPU3 -- Node0 NIC3 -- Leaf3 -- Node1 NIC3 -- Node1 GPU3
```

- DeepEP performs expert-parallel dispatch/combine and uses GPU communication kernels for MoE traffic.
  - DeepEP states that it focuses on expert parallelism and RDMA/NVLink communication for MoE dispatch and combine: <https://github.com/deepseek-ai/DeepEP>.
  - A typical dispatch optimization deduplicates a token after RDMA arrival and then replicates it locally over NVLink.

```text
  token --RDMA--> GPU0 --NVLink copy--> GPU1
                              |-------> GPU2
                              |-------> GPU3
```

- Link-aggregation systems such as FlexLink attempt to combine NVLink, PCIe, and RDMA NIC bandwidth.
  - FlexLink proposes aggregating heterogeneous links into a single communication fabric: <https://arxiv.org/abs/2510.15882>.
  - NIMBLE similarly routes traffic through intermediate GPUs and rail-matched NICs for multi-path balancing: <https://arxiv.org/abs/2604.00317>.

```text
  GPU0 --NVLink--> GPU1 --PCIe--> NIC1
    |              GPU2 --PCIe--> NIC2
    |              GPU3 --PCIe--> NIC3
    |
    +----------------PCIe-------> NIC0
```

- NCCL GIN and NCCL EP show another trend: device-initiated communication and GPU-controlled networking.
  - NCCL GIN presents GPU-Initiated Networking for NCCL Device API: <https://arxiv.org/abs/2511.15076>.
  - NCCL EP proposes a unified expert-parallel API based on NCCL Device API: <https://arxiv.org/abs/2603.13606>.
- These systems validate the importance of bridging NVLink and RDMA, but they often rely on SM-resident forwarding kernels or other GPU-side communication code.

## Problem Statement

- SM-based forwarding has three costs.
  - It consumes SM resources that could otherwise run model computation.
  - It creates unpredictable interference between communication kernels and background compute kernels.
  - It makes communication performance depend on kernel scheduling, occupancy, and SM availability.
- SM-free and SM-light communication is already becoming important.
  - NCCL 2.27 reports SHARP-enabled collectives that reduce SM usage by offloading aggregation to NVLink and InfiniBand fabrics: <https://developer.nvidia.com/blog/enabling-fast-inference-and-resilient-training-with-nccl-2-27/>.
  - DeepEP V2 advertises experimental 0-SM CP with Copy Engine and 0-SM RDMA primitives in its README: <https://github.com/deepseek-ai/DeepEP>.
  - CUDA exposes Copy Engine-based memory movement through APIs such as `cudaMemcpyAsync` and `cudaMemcpyBatchAsync`: <https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY.html>.
- The missing piece is a programmable bridge that can coordinate Copy Engine progress with RDMA operations at small chunk granularity.
- Research question:
  - Can we use GPU Copy Engines to bridge NVLink and RDMA traffic with near-SM-free data movement, while preserving overlap, ordering, and high message rate?

## Key Challenge: Overlapping NVLink Copy and RDMA

- The basic pipeline is straightforward.
  - Split a large message into KB-scale chunks.
  - Use the Copy Engine to move chunk i across NVLink.
  - As soon as chunk i is visible at the RDMA source GPU, post an RDMA operation for chunk i.
  - Keep Copy Engine movement and RDMA transfer overlapped.

```text
Time --->

  Copy Engine:  copy c0 | copy c1 | copy c2 | copy c3 | ...
                     |        |        |        |
  RDMA NIC:           send c0 | send c1 | send c2 | send c3 | ...
```

- The difficulty is not bulk copy bandwidth.
  - The difficulty is exposing fine-grained progress and issuing many small dependent operations efficiently.
- Public CUDA APIs are not designed for this control loop.
  - CUDA Graphs can batch submissions, but graph capture and instantiation have non-trivial overhead and are not a natural fit for dynamic per-chunk progress: <https://docs.nvidia.com/cuda/cuda-c-programming-guide/index.html#cuda-graphs>.
  - `cudaMemcpyBatchAsync` can submit many copies in one API call, but the public completion API gives a whole-batch event rather than per-copy progress: <https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY.html#group__CUDART__MEMORY_1g6126baf5d881835091c59e48890d6854>.
- RDMA already has a mature doorbell-batching model.
  - `ibv_post_send` posts a linked list of work requests to a send queue: <https://man7.org/linux/man-pages/man3/ibv_post_send.3.html>.
  - NIC doorbells typically point the NIC to WQEs already prepared in host memory; some Mellanox/NVIDIA devices also have fast paths such as BlueFlame for inline WQE submission.
- GPUs need batching even more than NICs in this setting.
  - A GPU doorbell causes the GPU PBDMA path to fetch GPFIFO entries and then push-buffer commands before work reaches the Copy Engine.
  - If each small chunk requires a separate CUDA API call or doorbell, launch overhead can dominate.

## Host-GPU Interface Model

- Prior work has shown that CUDA streams are a userspace driver abstraction, while the GPU-facing submission path uses channels, runlists, GPFIFO entries, push buffers, and doorbells.
  - `Demystifying NVIDIA GPU Internals to Enable Reliable GPU Management` studies NVIDIA GPU scheduling internals: <https://ieeexplore.ieee.org/document/10568069>.
  - `Revealing NVIDIA Closed-Source Driver Command Streams for CPU-GPU Runtime Behavior Insight` instruments the open kernel driver and reconstructs command streams: <https://arxiv.org/abs/2604.26889>.
  - `cuda_ioctl_sniffer` demonstrates launching CUDA kernels without using the CUDA driver runtime: <https://github.com/geohot/cuda_ioctl_sniffer>.

```text
User Application           CUDA Runtime / UMD                         GPU
+----------------+         +---------------------------+              +------------------+
| CUDA Stream 0 --+-------> | Scheduler                 |              | Runlist 0         |
| CUDA Stream 1 --+-------> |                           |              |   -> Compute      |
+----------------+         |  -> Channel 0 ------------+------------> |                  |
                           |  -> Channel 1 ------------+------------> | Runlist 0         |
                           |  -> Channel 2 ------------+------------> | Runlist 1         |
                           |  -> Channel 3 ------------+------------> | Runlist 2         |
                           +---------------------------+              |                  |
                                                                      | Runlist 1         |
                                                                      |   -> Copy Engine  |
                                                                      | Runlist 2         |
                                                                      |   -> Copy Engine  |
                                                                      +------------------+
```

- A CUDA stream does not directly exist as a hardware stream between the kernel driver and the GPU.
  - The UMD lowers CUDA stream dependencies into cross-channel synchronization commands.
  - Copy Engine work and compute work may land on different channels and runlists.

## GPFIFO and Push Buffer Model

- A GPU channel contains a GPFIFO ring.
- Each GPFIFO entry points to a push buffer.
- Each push buffer contains a sequence of low-level GPU commands.

```text
Channel

  GPFIFO ring
  +---------+---------+---------+---------+---------+
  | entry 0 | entry 1 | entry 2 | entry 3 | entry 4 |
  +----+----+----+----+----+----+----+----+----+----+
       |         |         |         |
       |         |         |         +----> Push Buffer D: [cmd][cmd][cmd][cmd]
       |         |         +--------------> Push Buffer C: [cmd][cmd]
       |         +------------------------> Push Buffer B: [cmd][cmd][cmd]
       +----------------------------------> Push Buffer A: [cmd][cmd]

  GP_GET points to the oldest unconsumed entry.
  GP_PUT points to the producer tail.
```

- GPU doorbell sequence.

```text
CPU                         GPU PBDMA                    Copy Engine / Compute
 |                             |                                  |
 | MMIO doorbell:              |                                  |
 | 32-bit work token           |                                  |
 | runlist_id + channel_id     |                                  |
 |---------------------------->|                                  |
 |                             | read GP_PUT                      |
 |                             |---------------------------------> |
 |                             | read GPFIFO entries              |
 |                             |---------------------------------> |
 |                             | read push-buffer commands        |
 |                             |---------------------------------> |
 |                             |                                  | execute commands
```

- RDMA NIC doorbell sequence.

```text
CPU                         RDMA NIC
 |                             |
 | prepare WQEs in SQ          |
 |                             |
 | MMIO doorbell:              |
 | QP number + opcode +        |
 | old SQ tail + new SQ tail   |
 |---------------------------->|
 |                             | DMA-read WQEs from SQ
 |                             |---------------------> host memory
 |                             |
 |                             | execute RDMA operation
```

- The GPU submission path usually requires more dependent metadata fetches than the NIC path.
- Therefore, one Copy Engine doorbell should carry many per-chunk copy-and-notify commands.

## Observed CUDA Async Operation Lowering

- We used `geohot/cuda_ioctl_sniffer`-style tracing to inspect how CUDA async copy APIs are lowered into GPU command streams.
- The initial experiment observed Host-to-Device copies on Ampere; Device-to-Device NVLink copies should be repeated once suitable multi-GPU NVLink nodes are available.
- Test code pattern:

```cuda
cudaMemcpyBatchAsync(dst_list, src_list, size_list, count, attrs, attrsIdxs, numAttrs, stream);
cudaEventRecord(event, stream);
```

- Observed lowering summary:

| CUDA API | GPU-facing artifact | Channel type | Notes |
|---|---|---|---|
| `cudaMemcpyBatchAsync` | One GPFIFO entry plus a push buffer containing multiple `CE_DMA_LAUNCH` commands | Copy Engine channel | Each `(dst, src, size)` pair becomes one Copy Engine DMA launch. |
| `cudaMemcpyBatchAsync` tail | `CE_SET_SEMAPHORE` plus `CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE` | Copy Engine channel | The semaphore is internal to CUDA and not directly exposed as per-copy progress. |
| `cudaEventRecord` | One GPFIFO entry plus a push buffer waiting on the internal semaphore | Compute channel | CUDA stream ordering becomes cross-channel synchronization. |
| `cudaEventRecord` tail | Report semaphore visible to `cudaEventQuery` | Compute channel | The user sees whole-operation completion rather than per-chunk progress. |

- Key implication:
  - CUDA already emits Copy Engine semaphores and release fences internally.
  - The public API hides the fine-grained progress signal that we need for chunk-level RDMA pipelining.

## Proposed Solution

- Build a CUDA-compatible shim layer that can submit custom Copy Engine push buffers while coexisting with CUDA Runtime and UMD state.
- The shim does not aim to replace CUDA.
  - CUDA still owns context creation, memory allocation, stream setup, and normal computation.
  - The shim owns a small number of Copy Engine channels and emits specialized copy-and-notify command sequences.
- The feasibility argument is based on existing public artifacts.
  - NVIDIA's open GPU kernel modules expose parts of the kernel driver interface: <https://github.com/NVIDIA/open-gpu-kernel-modules>.
  - `cuda_ioctl_sniffer` shows that CUDA work can be submitted without the CUDA driver runtime in controlled settings: <https://github.com/geohot/cuda_ioctl_sniffer>.
  - The Mesa NVK userspace driver and nouveau stack demonstrate that open userspace/kernel GPU command submission stacks can exist outside vendor CUDA UMDs: <https://docs.mesa3d.org/drivers/nvk.html>, <https://nouveau.freedesktop.org/>.

## Copy Engine to RDMA Bridge

- The bridge emits one Copy Engine push buffer containing repeated copy, semaphore, and release-fence commands.
- For each chunk i:
  - The Copy Engine copies chunk i over NVLink or PCIe peer access.
  - The Copy Engine writes a host-visible semaphore value i.
  - The Copy Engine issues a release fence so the copied data becomes visible before the semaphore update is consumed.
  - The CPU or communication proxy polls the semaphore and posts the RDMA work request for chunk i.

```text
Custom Copy Engine push buffer

  [CE_DMA_LAUNCH chunk 0]
  [CE_SET_SEMAPHORE value = 0]
  [CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE]

  [CE_DMA_LAUNCH chunk 1]
  [CE_SET_SEMAPHORE value = 1]
  [CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE]

  [CE_DMA_LAUNCH chunk 2]
  [CE_SET_SEMAPHORE value = 2]
  [CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE]

  ...
```

- Runtime pipeline:

```text
GPU A memory                    GPU B memory                    NIC / Network
    |                                |                                |
    |  Copy Engine chunk copy        |                                |
    |------------------------------->|                                |
    |                                | semaphore = chunk_id           |
    |                                |---- host-visible notify ------>|
    |                                |                                | RDMA send/write chunk
    |                                |                                |-------------------->
```

- Expected benefits:
  - One GPU doorbell can cover many chunks.
  - Per-chunk notifications avoid waiting for the whole `cudaMemcpyBatchAsync` batch.
  - No forwarding kernel needs to occupy SMs.
  - RDMA and NVLink transfers can be overlapped at chunk granularity.

## Correctness and Ordering

- GPUDirect RDMA has relaxed memory-ordering interactions with CUDA and GPU memory.
  - NVIDIA documents that only CUDA synchronization and work-submission APIs provide ordering of GPUDirect RDMA operations as observed by the GPU: <https://docs.nvidia.com/cuda/gpudirect-rdma/#synchronization-and-memory-ordering>.
- Our design must enforce a happens-before chain for each chunk.
  - Copy Engine writes chunk data.
  - Copy Engine release fence completes.
  - Copy Engine writes host-visible semaphore value.
  - CPU observes the semaphore value.
  - CPU posts RDMA operation for the chunk.
- We will validate this chain with adversarial tests.
  - Sender writes unique per-chunk patterns.
  - Receiver checks for torn, stale, or reordered chunks.
  - Tests sweep chunk sizes, queue depth, peer topology, and concurrent compute load.

## Research Contributions

- A measurement-driven model of Copy Engine command submission and completion behavior.
- A CUDA-compatible shim for custom Copy Engine push-buffer construction.
- A chunk-level Copy Engine to RDMA bridge that avoids SM-resident forwarding kernels.
- A comparison of three bridge designs:
  - Official CUDA Runtime API only.
  - SM-based forwarding kernels.
  - Reprogrammed Copy Engine forwarding.
- An application-level study on collectives and expert-parallel dispatch.

## Evaluation Plan

- Microbenchmarks:
  - GPU doorbell latency and amortized cost versus batch size.
  - RDMA doorbell latency and amortized cost versus WQE list size.
  - Copy Engine chunk copy latency and bandwidth over NVLink or PCIe peer paths.
  - Semaphore visibility latency from Copy Engine to CPU polling thread.
  - End-to-end overlap efficiency between Copy Engine transfers and RDMA sends.
  - SM occupancy, achieved compute throughput, and interference under background GEMM.
- Baselines:
  - CUDA Runtime-only shim using `cudaMemcpyAsync`, `cudaMemcpyBatchAsync`, `cudaEventRecord`, and `cudaEventQuery`.
  - SM-based forwarding shim modeled after GPU communication kernels used in systems such as DeepEP and NCCL GIN.
  - Existing collectives and communication libraries, including MPI, NCCL, and NCCL-GIN-style device-initiated networking when available.
- Application 1: Broadcast collective.
  - Root GPU receives or owns the broadcast buffer.
  - Copy Engine replicates the buffer to local GPUs over NVLink.
  - RDMA sends chunks to remote nodes as soon as the relevant local copy chunks complete.

```text
Root node

  GPU0 --Copy Engine/NVLink--> GPU1
    |-------------------------> GPU2
    |-------------------------> GPU3
    |
    +--RDMA chunks------------> Remote nodes
```

- Application 2: Expert-parallel dispatch.
  - Deduplicate tokens that arrive once over RDMA but are needed by multiple local GPUs.
  - Use Copy Engine replication instead of an SM copy kernel.
  - Evaluate with synthetic token distributions and traces collected from MoE inference.

```text
Remote expert traffic

  token --RDMA--> GPU0 staging buffer
                       |
                       +--Copy Engine/NVLink--> GPU1 expert input
                       +--Copy Engine/NVLink--> GPU2 expert input
                       +--Copy Engine/NVLink--> GPU3 expert input
```

## Risks and Mitigations

- Risk: undocumented GPU command formats may change across GPU generations or driver versions.
  - Mitigation: start with a narrow hardware/software matrix and validate command streams against observed CUDA-generated commands.
- Risk: CPU polling may become the bottleneck for very small chunks.
  - Mitigation: use chunk coalescing, semaphore stride tuning, and RDMA WQE batching.
- Risk: memory-ordering bugs may appear only under high concurrency.
  - Mitigation: build stress tests with concurrent kernels, concurrent Copy Engine work, and randomized chunk schedules.
- Risk: coexistence with CUDA UMD may be fragile.
  - Mitigation: keep CUDA responsible for normal runtime state and allocate only a small, isolated command-submission path for the shim.

## Expected Outcome

- If successful, the project will show that GPU Copy Engines can serve as programmable data movers between NVLink and RDMA.
- The result would reduce SM interference for communication-heavy workloads such as collectives, MoE dispatch, and topology-aware traffic engineering.
- The broader implication is that GPU communication stacks should expose more explicit progress, batching, and notification primitives for non-SM data movement.
