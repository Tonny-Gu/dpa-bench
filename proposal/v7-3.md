# Bridging Intra- and Inter-node Networks with Reprogrammed GPU Copy Engines

## Abstract

- Modern distributed GPU systems are built on two high-performance communication domains:
  - **Intra-node GPU fabrics**, such as NVLink / NVSwitch, for high-bandwidth GPU-to-GPU transfers inside a server.
  - **Inter-node RDMA networks**, such as InfiniBand or RoCE, for low-latency communication across servers.

- These two domains are increasingly used together:
  - **NCCL PXN, 2022** uses NVLink to route GPU traffic toward better-affined NICs and rail-optimized paths. [[NVIDIA PXN blog, 2022](https://developer.nvidia.com/blog/doubling-all2all-performance-with-nvidia-collective-communication-library-2-12/)]
  - **DeepEP, 2025** targets high-throughput and low-latency MoE dispatch/combine, where tokens may move across nodes through RDMA and then be redistributed inside a node. [[DeepEP GitHub](https://github.com/deepseek-ai/DeepEP)]
  - **FuseLink, 2025** uses intra-server GPU links and relay GPUs to utilize multiple NICs for inter-server GPU communication. [[FuseLink, OSDI 2025](https://www.usenix.org/conference/osdi25/presentation/ren)]

- However, existing NVLink/RDMA bridges often rely on **SM-mediated forwarding**, where GPU kernels move or route data.

- This proposal explores a different bridge:
  - Use the GPU **Copy Engine** as an SM-free data relay between NVLink-domain movement and RDMA-domain movement to move chunks across GPUs inside a node.
  - Reprogram Copy Engine command streams so that each completed chunk releases a host-visible semaphore.
  - Let a CPU-side RDMA bridge post RDMA Work Requests as soon as Copy Engine chunks become ready.

- The core contribution is:

> **A reprogrammed Copy Engine based bridge that uses SM-free intra-node GPU data movement to feed inter-node RDMA transmission.**

---

## Motivation

- Multi-GPU systems have evolved into dense intra-node GPU fabrics:
  - NVIDIA NVLink / NVSwitch provide high-bandwidth GPU-to-GPU communication and are now central to large-scale AI systems. NVIDIA describes NVLink and NVLink Switch as scale-up interconnects for large model parallelism and high-bandwidth GPU communication. ([NVIDIA NVLink](https://www.nvidia.com/en-us/data-center/nvlink/))
  - Across nodes, systems still rely on scale-out networks such as InfiniBand or Ethernet/RoCE. NVIDIA’s NVSHMEM / GPUDirect Async discussion explicitly frames modern systems as using NVLink inside nodes and InfiniBand across nodes. ([NVIDIA Developer Blog, 2022](https://developer.nvidia.com/blog/improving-network-performance-of-hpc-systems-using-nvidia-magnum-io-nvshmem-and-gpudirect-async/))

- RDMA was designed around direct memory access through a network interface, not around GPU fabric interoperability.

- RDMA interoperability is already difficult inside the RDMA world:
  - Flor reports that RNICs from different vendors and generations can differ in control-plane behavior even when using the same RoCEv2 data-path specification. [[Flor, OSDI 2023](https://www.usenix.org/conference/osdi23/presentation/li-qiang)]
  - This makes direct interoperability between RDMA and proprietary GPU fabrics even less natural.

- Cache-coherent interconnects such as CXL point toward a cleaner future, but they are not the abstraction used by today’s GPU collective and RDMA stacks.
  - CXL is an industry-supported cache-coherent interconnect for processors, memory expansion, and accelerators. [[CXL Consortium](https://computeexpresslink.org/about-cxl/)]
  - Today’s high-performance GPU communication still relies heavily on explicit mechanisms such as CUDA APIs, NCCL, NVLink, GPUDirect RDMA, and RDMA verbs.

- Therefore, many systems build software bridges between the two domains. However, existing NVLink/RDMA bridges often rely on **SM-mediated forwarding**, where GPU kernels move or route data.

- The central question of this proposal:

> Can the GPU Copy Engine become this relay path, so that NVLink/RDMA bridging does not consume SM cycles?

## Existing NVLink/RDMA Bridges

### NCCL PXN: topology-aware relay through NVLink

- **NCCL PXN, 2022** lets a GPU communicate with a NIC through NVLink and then PCIe, instead of traversing CPU-socket paths such as QPI or UPI. [[NVIDIA PXN blog, 2022](https://developer.nvidia.com/blog/doubling-all2all-performance-with-nvidia-collective-communication-library-2-12/)]

```text
Poor GPU-NIC affinity:

  GPU1 <--PCIe--> NUMA1 <--UPI/QPI--> NUMA0 <--PCIe--> NIC0

PXN-style path:

  GPU1 <--NVLink--> GPU0 <--PCIe--> NIC0
```

- PXN also helps rail-optimized clusters:
  - A node may connect NIC `i` to leaf switch `i`.
  - PXN can move data inside the node first, then send it through the NIC that matches the target rail.
  - This reduces traffic through spine switches. [[NVIDIA PXN blog, 2022](https://developer.nvidia.com/blog/doubling-all2all-performance-with-nvidia-collective-communication-library-2-12/)]

```text
Before PXN:
  Node0:GPU0 -> NIC0 -> Leaf0 -> Spine -> Leaf3 -> NIC3 -> Node1:GPU3

After PXN:
  Node0:GPU0 -> NVSwitch -> Node0:GPU3 -> NIC3 -> Leaf3 -> Node1:NIC3 -> GPU3
```

### MoE dispatch: RDMA first, then NVLink redistribution

- Expert-parallel MoE communication naturally combines RDMA and NVLink:
  - Tokens may be routed across nodes through RDMA.
  - Once a node receives the relevant token data, data must be redistributed to local expert GPUs.
  - DeepEP focuses on high-throughput, low-latency all-to-all GPU kernels for MoE dispatch and combine, while targeting minimal SM occupation. [[DeepEP GitHub](https://github.com/deepseek-ai/DeepEP)]

```text
MoE token deduplication / redistribution:
  remote tokens -> RDMA -> GPU0 -> NVLink fanout -> GPU1, GPU2, GPU3
```

### FuseLink: relay GPUs and multiple NICs

- **FuseLink, 2025** uses intra-server GPU links and relay GPUs to utilize idle NICs.
  - It integrates into NCCL and reports up to 212 GB/s bandwidth between two inter-server GPUs. [[FuseLink, OSDI 2025](https://www.usenix.org/conference/osdi25/presentation/ren)]

```text
FuseLink-style multi-NIC relay:

  GPU0 --NVLink--> GPU1 --> NIC1
    |       |----> GPU2 --> NIC2
    |       +----> GPU3 --> NIC3
    +---------------------> NIC0
```

### Why Copy Engine relay?

- Existing systems show that bridging NVLink and RDMA is valuable.
- The remaining question is the relay mechanism:
  - SM relay kernels can interfere with background compute.
  - GPU-initiated networking is powerful but still uses GPU execution resources and requires specific software/hardware support.

- NCCL 2.28 introduced Copy Engine based collectives:
  - NVIDIA describes CE collectives as using Copy Engines to drive NVLink transfers and reduce SM resource contention.
  - This validates Copy Engine communication as a serious direction. [[NVIDIA NCCL 2.28 blog, 2025](https://developer.nvidia.com/blog/fusing-communication-and-compute-with-new-device-api-and-copy-engine-collectives-in-nvidia-nccl-2-28/)]

- This proposal extends the idea:

> Copy Engines should not only be used for intra-node collectives. They can also become the SM-free relay between NVLink-domain movement and RDMA-domain movement.

## Challenges

- The basic pipeline is straightforward.
  - Split a large message into KB-scale chunks.
  - Use the Copy Engine to move chunk i across NVLink.
  - As soon as chunk i is visible at the RDMA source GPU, post an RDMA operation for chunk i.
  - Keep Copy Engine movement and RDMA transfer overlapped.

```text
Time --->

  Copy Engine:  copy c0 | copy c1 | copy c2 | copy c3 | ...
                        |         |         |         |
  RDMA NIC:               send c0 | send c1 | send c2 | send c3 | ...
```

### Fine-grained completion granularity

- Public CUDA APIs expose completion at stream, event, or batch granularity.
- NVLink/RDMA pipelining needs **per-chunk progress**:
  - Split a buffer into KB-scale or MB-scale chunks.
  - Start RDMA for chunk `i` as soon as the Copy Engine finishes producing chunk `i`.
  - Avoid waiting for the whole Copy Engine batch to complete.

- `cudaMemcpyBatchAsync` is close, but not enough:
  - CUDA 12.8 added batch async memory copy APIs for variable-sized transfers between multiple source and destination buffers. ([CUDA Toolkit 12.8 Release Notes](https://docs.nvidia.com/cuda/archive/12.8.2/cuda-toolkit-release-notes/index.html))
  - CUDA’s runtime documentation says the batch as a whole executes in stream order, but copies inside the batch are not guaranteed to execute in a specific order; dependent copies inside a batch are undefined behavior. ([CUDA Runtime API Documentation](https://docs.nvidia.com/cuda/cuda-runtime-api/group__CUDART__MEMORY.html))
  - This makes it difficult to use public batch APIs for ordered per-chunk progress.

### GPU command submission overhead

- A naïve design would submit one Copy Engine operation per chunk:
  - `cudaMemcpyAsync(chunk 0)`
  - `cudaEventRecord(event 0)`
  - `cudaMemcpyAsync(chunk 1)`
  - `cudaEventRecord(event 1)`
  - …

- This is likely too expensive because each tiny operation can introduce CPU-side runtime/driver overhead and GPU command-submission overhead.
  - RDMA systems already treat doorbell batching as a core performance optimization.
    - Kalia et al., ATC 2016, describe doorbell batching as a way to reduce CPU-generated MMIOs when multiple WQEs can be issued to a QP. [[Kalia et al., ATC 2016](https://www.usenix.org/system/files/conference/atc16/atc16_paper-kalia.pdf)]
  - NVIDIA’s CUDA Graphs material describes GPU operation submission overhead as microsecond-scale and motivates graphs as a way to launch multiple operations through one CPU operation. ([NVIDIA CUDA Graphs Blog, 2019](https://developer.nvidia.com/blog/cuda-graphs/))
  - CUDA Graphs reduce repeated launch overhead, but graph construction and instantiation remain separate preprocessing steps whose cost depends on graph structure. NVIDIA’s CUDA 12.6 graph performance writeup explicitly discusses construction, instantiation, and launch overhead improvements. ([NVIDIA CUDA Graphs Performance Blog, 2024](https://developer.nvidia.com/blog/constant-time-launch-for-straight-line-cuda-graphs-and-other-performance-enhancements/))

- For our use case, we need:
  - One GPU doorbell for many Copy Engine commands.
  - Per-chunk semaphore release inside the batched command stream.
  - Progress visibility without one CUDA event per chunk.  

### Cross-domain ordering and visibility

- The correctness condition is subtle:

```text
CE writes GPU memory
CE executes release fence
CE writes host-visible semaphore
CPU observes semaphore
CPU posts RDMA work request
NIC reads GPU memory
```

- The system must ensure:
  - The CPU does not post RDMA before the Copy Engine has completed the chunk.
  - The NIC does not read stale or partially written GPU data.

## Host-GPU Interface Background

### CUDA streams are not the hardware scheduling primitive

- CUDA programmers see streams.
- The CUDA Runtime and User Mode Driver lower streams into hardware-facing structures:
  - Channels
  - Runlists
  - GPFIFO rings
  - Push buffers
  - Engine-specific command streams
  - Cross-channel semaphores

- Prior work on NVIDIA GPU internals shows that GPU scheduling involves channels, runlists, and engines, and that every GPU-engine-using operation goes through a channel. ([Demystifying NVIDIA GPU Internals, RTAS 2024](https://www.cs.unc.edu/~jbakita/rtas24.pdf))
- Recent command-stream reverse engineering describes NVIDIA command submission as a path where the driver writes pushbuffer commands, enqueues GPFIFO entries, advances `GP_PUT`, and rings a doorbell; then PBDMA fetches the GPFIFO entry and pushbuffer commands. ([Revealing NVIDIA Closed-Source Driver Command Streams, arXiv 2026](https://arxiv.org/html/2604.26889v1))

```text
+------------------+       +----------------------+       +--------------------------------+
| User Application |       | CUDA Runtime & UMD   |       | GPU                            |
|                  |       |                      |       |                                |
|  Stream 0 -------+-----> |  Scheduler           |       |                                |
|  Stream 1 -------+-----> |     |                |       |                                |
|                  |       |     v                |       |                                |
|                  |       |  Ch0 --------------- +-----> |  Ch0-1 -> Runlist 0 -> Compute |
|                  |       |  Ch1 --------------- +--+    |                                |
|                  |       |  Ch2 --------------- +-----> |  Ch2   -> Runlist 1 -> CE0     |
|                  |       |  Ch3 --------------- +-----> |  Ch3   -> Runlist 2 -> CE1     |
+------------------+       +----------------------+       +--------------------------------+
```

- In this model:
  - A CUDA stream is a UMD-level abstraction.
  - A channel is closer to the hardware submission unit.
  - A runlist controls how channels are scheduled onto GPU engines.
  - Copy Engine work is represented as engine-specific commands in pushbuffers.

### GPFIFO and Push Buffer

- A GPU channel contains a GPFIFO ring.
- Each GPFIFO entry points to a push buffer.
- Each push buffer contains a sequence of low-level GPU commands.

```text
Channel

  USERD:
    GP_PUT = producer index, points to the oldest unconsumed entry.
    GP_GET = consumer index, points to the producer tail.

  GPFIFO ring
  +---------+---------+---------+---------+---------+
  | entry 0 | entry 1 | entry 2 | entry 3 | entry 4 |
  +----+----+----+----+----+----+----+----+----+----+
       |         |         |         |
       |         |         |         +----> Push Buffer D: [cmd][cmd][cmd][cmd]
       |         |         +--------------> Push Buffer C: [cmd][cmd]
       |         +------------------------> Push Buffer B: [cmd][cmd][cmd]
       +----------------------------------> Push Buffer A: [cmd][cmd]
```

- A typical GPU command submission path is:

```text
CPU / UMD:
  1. Write pushbuffer commands.
  2. Fill one GPFIFO entry pointing to the pushbuffer segment.
  3. Advance GP_PUT.
  4. Ring GPU doorbell through MMIO.

GPU / PBDMA:
  5. Fetch GP_PUT / channel state.
  6. Fetch GPFIFO entry.
  7. Fetch pushbuffer command stream.
  8. Parse commands and dispatch them to Compute / Copy Engine.
```

- This is the interface we want to control.
- Public CUDA APIs hide it.

### GPU doorbell vs RDMA NIC doorbell

- GPU and RDMA NIC submission look superficially similar:
  - Both use user-space command construction.
  - Both can notify hardware through MMIO doorbells.
  - Both avoid a kernel transition on the hot submission path once resources are mapped.

- But the post-doorbell paths are different.

```text
GPU doorbell path:

CPU                         Host Memory                         GPU PBDMA
 |                              |                                    |
 | write USERD / GP_PUT,        |                                    |
 | GPFIFO entries,              |                                    |
 | push-buffer commands         |                                    |
 |----------------------------->|                                    |
 |                              |                                    |
 | MMIO doorbell:               |                                    |
 | runlist_id + channel_id      |                                    |
 |------------------------------------------------------------------>|
 |                              |                                    |
 |                              | DMA read                           |
 |                              | USERD / GP_PUT ------------------->|
 |                              |                                    |
 |                              | DMA read                           |
 |                              | GPFIFO entries ------------------->|
 |                              |                                    |
 |                              | DMA read                           |
 |                              | push-buffer commands ------------->|
 |                              |                                    | dispatch to CE / compute
 |                              |                                    | execute commands
```

```text
RDMA NIC doorbell path:

CPU                         Host Memory                         RDMA NIC
 |                              |                                    |
 | write WQEs into SQ           |                                    |
 | update doorbell record       |                                    |
 |----------------------------->|                                    |
 |                              |                                    |
 | MMIO doorbell:               |                                    |
 | QP + opcode + SQ tail        |                                    |
 |------------------------------------------------------------------>|
 |                              |                                    |
 |                              | DMA read                           |
 |                              | WQEs from SQ --------------------->|
 |                              |                                    | execute RDMA operation
 |                              |                                    | read GPU memory via GDR
 |                              |                                    | transmit packets
```

- RDMA systems have mature batching techniques:
  - Doorbell batching lets multiple WQEs use one Doorbell MMIO.
  - Kalia et al. describe doorbell batching as reducing CPU-generated MMIOs and PCIe transactions; they also distinguish WQE-by-MMIO from Doorbell mode, where the NIC reads WQEs through DMA. ([Kalia et al., ATC 2016](https://www.usenix.org/system/files/conference/atc16/atc16_paper-kalia.pdf))
  - The same paper notes that Mellanox terminology uses “BlueFlame” for WQE-by-MMIO and “Doorbell” for the DMA-read path. ([Kalia et al., ATC 2016](https://www.usenix.org/system/files/conference/atc16/atc16_paper-kalia.pdf))

- Our hypothesis:
  - **GPU Copy Engine submission is even more sensitive to unbatched doorbells than RNIC posting**, because a GPU doorbell triggers a multi-stage PBDMA path through `USERD`, GPFIFO, and pushbuffer fetches.
  - Therefore, we should not submit one Copy Engine operation per chunk.
  - Instead, we should submit one batched Copy Engine pushbuffer that contains many chunk copies and many per-chunk progress releases.

## Preliminary Investigation: CUDA Async Operations

- We use `geohot/cuda_ioctl_sniffer` to inspect CUDA Runtime / UMD interaction with GPU command submission.
  - The repository states that it can launch a CUDA kernel without using the CUDA driver runtime, and includes code for pushing command queues and replacing CUDA initialization. [[cuda_ioctl_sniffer](https://github.com/geohot/cuda_ioctl_sniffer)]
  - Recent command-stream work also supports the feasibility of identifying pushbuffer, GPFIFO, and semaphore structures and injecting customized commands. [[Revealing NVIDIA Closed-Source Driver Command Streams, 2026](https://arxiv.org/html/2604.26889v1)]

- We inspect this code pattern:

```cuda
cudaMemcpyBatchAsync(dst=[...], src=[...], kind=H2D, stream=0);
cudaEventRecord(event, stream=0);
```

### cudaMemcpyBatchAsync

- For `cudaMemcpyBatchAsync`, our preliminary observation is:

```text
Copy Engine channel:
  new GPFIFO entry
  pushbuffer commands:

  [
    CE_DMA_LAUNCH,
    CE_DMA_LAUNCH,
    ...
    CE_SET_SEMAPHORE,
    CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE
  ]

  one GPU doorbell
```

- Interpretation:
  - Each `(dst, src)` pair becomes one `CE_DMA_LAUNCH`.
  - The end of the batch sets an internal CUDA semaphore.
  - A memory release fence is issued at the end.
  - The whole batch uses one GPU doorbell.

### cudaEventRecord

- For `cudaEventRecord`, our preliminary observation is:

```text
Compute channel:
  new GPFIFO entry
  pushbuffer commands:

  [
    GPFIFO_WAIT_AND_ACQUIRE_SEMAPHORE,
    COMP_SET_REPORT_SEMAPHORE_AND_RELEASE
  ]

  one GPU doorbell
```

- Interpretation:
  - CUDA stream order becomes cross-channel semaphore synchronization.
  - The Compute channel waits for the Copy Engine channel’s internal semaphore.
  - The Compute channel writes a user-visible report semaphore.
  - `cudaEventQuery` eventually observes the user-visible completion.

- This is very close to what we need, but not enough:
  - CUDA already batches Copy Engine DMA commands.
  - CUDA already releases semaphores.
  - CUDA already lowers stream order into cross-channel synchronization.
  - But CUDA exposes only coarse completion for the batch.

## Proposed Design

### Key idea

- Instead of using public CUDA batch APIs, construct a Copy Engine Push buffer like this:

```text
Current CUDA-like batch:

  CE_DMA_LAUNCH(chunk 0)
  CE_DMA_LAUNCH(chunk 1)
  CE_DMA_LAUNCH(chunk 2)
  ...
  CE_SET_SEMAPHORE(batch_done)
  CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE

Our CE/RDMA bridge:

  CE_DMA_LAUNCH(chunk 0)
  CE_SET_SEMAPHORE(progress = 0)
  CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE

  CE_DMA_LAUNCH(chunk 1)
  CE_SET_SEMAPHORE(progress = 1)
  CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE

  CE_DMA_LAUNCH(chunk 2)
  CE_SET_SEMAPHORE(progress = 2)
  CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE

  ...
```

- The important shift:
  - We do not use the Copy Engine only as a bulk-copy backend.
  - We reprogram the Copy Engine command stream into a relay protocol between NVLink and RDMA.

### Shim layer

- CUDA does not expose APIs for:
  - manually selecting Copy Engine channels,
  - constructing Copy Engine pushbuffers,
  - inserting arbitrary CE semaphore methods,
  - ringing GPU doorbells with custom GPFIFO entries.

- Therefore, we propose a shim layer.

- The shim handles:
  - Copy Engine channel setup or discovery.
  - GPFIFO construction.
  - Pushbuffer construction.
  - CE DMA commands.
  - Per-chunk semaphore updates.
  - Release fences.
  - Doorbell submission.

- The shim does not handle:
  - full CUDA UMD replacement,
  - general CUDA stream scheduling,
  - CUDA kernel launch,
  - full CUDA Graph semantics,
  - multi-rail aggregation in this proposal.

- Feasibility evidence:
  - `cuda_ioctl_sniffer` demonstrates CUDA-less command submission experiments. [[cuda_ioctl_sniffer](https://github.com/geohot/cuda_ioctl_sniffer)]
  - Command-stream reverse engineering shows how pushbuffer, GPFIFO, and semaphore buffers can be identified and manipulated. [[Revealing NVIDIA Closed-Source Driver Command Streams, 2026](https://arxiv.org/html/2604.26889v1)]
  - Nouveau / NVK show that community-maintained NVIDIA userspace/kernel graphics stacks are possible, although their goals differ from CUDA CE/RDMA bridging. [[Nouveau](https://nouveau.freedesktop.org/)]
  
### Bridge

- The bridge is a single component built on the restricted shim layer above.
- It combines Copy Engine command submission with RDMA posting and completion handling.
- The same bridge can operate in both send and receive directions:

```text
+---------------------------------------------------------------------+
| CE/RDMA Bridge                                                      |
| built on the restricted shim layer                                  |
|                                                                     |
| Send path                                                           |
|   CE:   local GPU -> NVLink/peer copy -> NIC-affine GPU memory      |
|         write per-chunk progress semaphore                          |
|   RDMA: poll progress -> batch Send WRs -> ring NIC doorbell        |
|         NIC reads GPU memory through GPUDirect RDMA                  |
|                                                                     |
| Receive path                                                        |
|   RDMA: prepare receive target / Recv WRs -> ring NIC doorbell      |
|         NIC places incoming chunks into NIC-affine GPU memory        |
|   CE:   poll RDMA completion/progress -> NVLink/peer fanout         |
|         write per-chunk progress semaphore                          |
+---------------------------------------------------------------------+
```

## Evaluation Plan

- Microbenchmarks:
  - GPU doorbell latency and amortized cost versus batch size.
  - RDMA doorbell latency and amortized cost versus WQE list size.
  - Copy Engine chunk copy latency and bandwidth over NVLink or PCIe peer paths.
  - Semaphore visibility latency from Copy Engine to CPU polling thread.
  - End-to-end overlap efficiency between Copy Engine transfers and RDMA sends.
  - SM occupancy, achieved compute throughput, and interference under background GEMM.
- Baselines:
  - CUDA Runtime-only shim using `cudaMemcpyAsync`, `cudaMemcpyBatchAsync`, `cudaEventRecord`, and `cudaEventQuery`.
  - SM-based forwarding shim modeled after GPU communication kernels used in systems such as DeepEP and NCCL GIN.
  - Existing collectives and communication libraries, including MPI, NCCL, and NCCL-GIN-style device-initiated networking when available.
- Application 1: Broadcast collective.
  - Root GPU receives or owns the broadcast buffer.
  - Copy Engine replicates the buffer to local GPUs over NVLink.
  - RDMA sends chunks to remote nodes as soon as the relevant local copy chunks complete.
- Application 2: Expert-parallel dispatch.
  - Deduplicate tokens that arrive once over RDMA but are needed by multiple local GPUs.
  - Use Copy Engine replication instead of an SM copy kernel.
  - Evaluate with synthetic token distributions and traces collected from MoE inference.

## Related Work

### Topology-aware GPU/NIC communication

- **NCCL PXN, 2022**
  - Uses NVLink plus PCIe to let GPUs reach better NIC paths and rail-optimized network paths.
  - Closest motivation for NIC-affinity relay.
  - Difference: PXN is NCCL-internal, while this proposal studies an explicit Copy Engine based bridge for chunked RDMA overlap. [[NVIDIA PXN blog, 2022](https://developer.nvidia.com/blog/doubling-all2all-performance-with-nvidia-collective-communication-library-2-12/)]

- **FuseLink, 2025**
  - Uses intra-server GPU links and relay GPUs to improve multi-NIC utilization.
  - Difference: this proposal does not evaluate multi-rail aggregation in the first testbed; it targets Copy Engine relay. [[FuseLink, OSDI 2025](https://www.usenix.org/conference/osdi25/presentation/ren)]

### MoE and expert-parallel communication

- **DeepEP, 2025**
  - Provides MoE dispatch/combine GPU kernels and targets zero or minimal SM occupation.
  - Difference: this proposal specifically studies Copy Engine based intra-node relay and CE-to-RDMA pipelining. [[DeepEP GitHub](https://github.com/deepseek-ai/DeepEP)]

### Copy Engine based communication

- **NCCL CE Collectives, 2025**
  - Uses Copy Engines to drive NVLink transfers and reduce SM contention for selected data-movement collectives.
  - Difference: NCCL CE collectives focus on NVLink-domain collectives; this proposal uses Copy Engines to bridge NVLink-domain movement with RDMA-domain movement. [[NVIDIA NCCL 2.28 blog, 2025](https://developer.nvidia.com/blog/fusing-communication-and-compute-with-new-device-api-and-copy-engine-collectives-in-nvidia-nccl-2-28/)]

### GPU-initiated networking

- **NCCL GIN / Device API, 2025**
  - Lets GPU code participate directly in network operations through NCCL Device API.
  - Difference: GIN is a GPU-initiated networking path; this proposal keeps Copy Engine as the relay engine and uses CPU-assisted RDMA posting in the first prototype. [[NVIDIA NCCL 2.28 blog, 2025](https://developer.nvidia.com/blog/fusing-communication-and-compute-with-new-device-api-and-copy-engine-collectives-in-nvidia-nccl-2-28/)]

### CUDA batching and runtime APIs

- **CUDA Graphs, 2019–2024**
  - Batch GPU work into graphs and reduce repeated launch overhead.
  - Difference: CUDA Graphs do not expose ordered per-chunk CE completion inside a streaming copy batch. [[NVIDIA CUDA Graphs blog](https://developer.nvidia.com/blog/cuda-graphs/)]

- **`cudaMemcpyBatchAsync`, 2025**
  - Supports batched memory copies, but public documentation says copies inside a batch have no specific ordering guarantee.
  - Difference: this proposal needs ordered per-chunk CE release inside the command stream. [[CUDA runtime documentation](https://nvidia.github.io/cuda-python/cuda-bindings/latest/module/runtime.html)]

### RDMA doorbell batching

- **Kalia et al., 2016**
  - Characterizes RDMA optimizations such as doorbell batching, BlueFlame, and reducing CPU-generated MMIOs.
  - Difference: this proposal applies the batching lesson to the GPU Copy Engine submission path, where PBDMA, GPFIFO, and pushbuffer fetching make unbatched GPU doorbells unattractive. [[Kalia et al., ATC 2016](https://www.usenix.org/system/files/conference/atc16/atc16_paper-kalia.pdf)]

### GPU command-stream reverse engineering

- **Demystifying NVIDIA GPU Internals, 2024**
  - Studies NVIDIA GPU engines, channels, runlists, and Copy Engine behavior.
  - Relevance: provides the hardware mental model for CE as an independent data-movement engine. [[Demystifying NVIDIA GPU Internals, RTAS 2024](https://www.cs.unc.edu/~jbakita/rtas24.pdf)]
