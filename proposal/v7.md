# Bridging Intra- and Inter-node Networks with Reprogrammed GPU Copy Engines

## Introduction

（大概是这个介绍思路，相关工作要用link引起来）

- 简单介绍一下多GPU和GPU内的intra-node network是怎么兴起的
- 然后简单介绍一下RDMA（inter-node network）是一种诞生于GPGPU以前的技术，然后有诸多原因限制了RDMA和inter-node network的互操作性，原因有非常多（你也帮我找找），比如
    - RDMA自己的跨vendor跨NIC型号的互操作性就不是很好（找一下相关工作），更别说RDMA和NVLink的跨vendor了。
    - cache coherent的PCIe，也就是CXL，还没有普及
- 然而很多工作有在使用GPU的SM转发RDMA的数据，比如（你也帮我找找）
    - NCCL PXN用来做topology-aware traffic engineering，比如
        - GPU和NIC的affinity不好，跨了NUMA
            - 优化前 GPU1 <--PCIe--> NUMA1 <--UPI--> NUMA0 <--PCIe--> NIC0
            - 优化后 GPU1 <--NVLink--> GPU0 <--PCIe--> NIC0
        - 做rail optimization，减小Spine Switch的流量（NCCL假定了网络拓扑，即Node x NIC y连接到Leaf y上）
            - 优化前 Node0 GPU0 <--> Node0 NIC0 <--> Leaf0 <--> Spine <--> Leaf3--> Node1 NIC3 <--> Node1 GPU3
            - 优化后 Node0 GPU0 <--NVSwitch--> Node0 GPU3 <--> Node0 NIC3 <--> Leaf3 <--> Node1 NIC3 <--> Node1 GPU3
    - DeepEP在dispatch的时候做token去重，即
        - token --RDMA--> GPU0 --NVLink复制--> GPU1,2,3
    - 以及FuseLink用NVLink将多个RDMA NIC聚合起来
        - GPU0 --NVLink--> GPU1,2,3 --> NIC1,2,3
        -  |---> NIC0
- 先前的工作全部需要占用SM来转发数据，这不仅需要占用SM计算资源，会与background的计算互相产生干扰
- 因此SM-free的collective研究正在兴起，比如NCCL CE Collectives，它利用了GPU上的Copy Engine，一个广泛存在于GPU上的用于Host到GPU（H2D）和GPU之间（P2P）传输数据的DMA引擎，来做intra-node的非计算的集合通信（即AllReduce和ReduceScatter以外的Collective）。但inter-node的集合通信目前还不支持。
- 因此很自然的我们可以想到用Copy Engine来搬运RDMA和NVLink的流量。

## Challenges

- 显而易见最基本的要求又最困难的地方就是将NVLink和RDMA的传输overlap起来。
- 一个直接的想法就是我们将要传输的数据切分为数KB的chunk，当每当Copy Engine完成一个chunk的传输，就发起RDMA的传输。
- 然而目前Copy Engine的公开API对小尺寸的流式传输和通知并不友好。
- 比如CUDA提供的doorbell batching机制非常有限，而doorbell batching在RDMA是一个非常常用的提升message rate的技巧，有很多工作有提过（你找一下相关工作）。
- 而与此同时，我们认为GPU比RDMA NIC更需要doorbell batching，因为GPU的doorbell开销比RDMA NIC要大得多。

### Host-GPU Interface

- 有一些先前工作(Demystifying NVIDIA GPU Internals to Enable Reliable GPU Management，和Revealing NVIDIA Closed-Source Driver Command Streams for CPU–GPU Runtime Behavior Insight)研究了闭源的userspace CUDA runtime / driver (UMD)与开源的kernel driver的交互，以及GPU内部的行为。
- NVIDIA的Host-GPU Interface是这样的
    - 画一个图，从左到右是
        - User Application
            - 有上到下有两个Stream， Stream 0和Stream 1
        - CUDA Runtime & UMD
            - 从左到右
                - 一个Scheduler
                    - 两个Stream指向Scheduler
                - 从上到下四个Channel
                    - Scheduler指向四个Channel，Ch0-3
        - GPU
            - 从左到右
                - 从上到下三个Runlist
                    - Ch0-1指向Runlist0
                    - Ch2指向Runlist1
                    - Ch3指向Runlist2
                - 从上到下是Compute和Copy Engine
                    - Runlist0指向Compute
                    - Runlist1-2指向Copy Engine
- 注意CUDA Stream是一个CUDA UMD的概念，在Driver和GPU之间是没有CUDA Stream这个概念的
- 当然Channel里还有GPFIFO和Push Buffer
    - 画一个图说
        - GPFIFO是个ring buffer，有GP_PUT和GP_GET，分别是队尾和队头
        - 然后GPFIFO从上到下有几个entries
        - 然后每个entry又指向右边一个Push Buffer
        - Push Buffer里从左到右有数量不同的Commands
- 然后说GPU和RDMA NIC一样，向他们发送命令不需要经过kernel，直接MMIO写入Doorbell
- 然后画一个时序图
    1. CPU MMIO写入 ring GPU的doorbell， 内容是32bit的work submit token，编码了runlist_id和channel_id
    2. GPU的PBDMA读GP_PUT
    3. GPU的PBDMA读GPFIFO的entries
    4. GPU的PBDMA读Push Buffer的commands
- 作为对比，RDMA NIC的doorbell过程是（再画一个时序图）
    1. CPU MMIO写入 ring NIC的doorbell， 内容是64bit的token，编码了QP Num，opcode，SQ（Send Queue）的原队尾，SQ的新增长度
    2. NIC的DMA读SQ的WQE（Work Queue Element）
- 甚至ConnectX还有BlueFlame的fast path，能直接通过MMIO写入WQE，直接省略step 2
- 因此我们认为GPU一次Doorbell的开销比NIC的开销要大得多

### CUDA Runtime and UMD API

- 与此同时CUDA Runtime和UMD API对doorbell batching提供的支持也非常有限。CUDA Graph是其中一种能进行doorbell batching的手段，但是CUDA Graph的record开销也是数微秒到数百微秒级的，取决于Graph有多少个node。
- 另一种Copy Engine能用到的手段，也是NCCL CE使用的，就是CUDA 12.8 (2025 Jan)开始支持的`cudaMemcpyBatchAsync`接口，它可以一次性指定很多src和dst地址。然而根据公开的接口我们只能使用`cudaEventRecord`获得`cudaMemcpyBatchAsync`的整体完成事件，而无法获取`cudaMemcpyBatchAsync`的实时进度。
- 这就让我们想用Copy Engine按chunk进行D2D复制（NVLink传输）变得很尴尬，因为我们希望知道每个chunk完成的时机，然后立刻进行RDMA传输，所以`cudaMemcpyBatchAsync`对我们并没有很大的帮助。

### Dive Deep Into CUDA Async Operations

- 我们使用了`geohot/cuda_ioctl_sniffer`这个工具研究了Host与GPU/Copy Engine交互的过程，结果非常有趣
- 我们先观察了用`cudaMemcpyBatchAsync`和`cudaEventRecord`把数据从Host传输到Ampere GPU的Host-GPU Interface的交互过程
    - Ampere 多GPU在NVLink上的D2D Copy等到多GPU节点可用后再观察
- 我们观察了这样的代码
```cuda
cudaMemcpyBatchAsync(dst=[...], src=[...], kind=H2D, stream=0)
cudaEventRecord(event, stream=0)
```
- 然后我们观察到了`cudaMemcpyBatchAsync`产生了
    - 一个新的GPFIFO entry，属于Copy Engine的channel
    - 一组PushBuffer的commands，简单来说包含`[CE_DMA_LAUNCH, CE_DMA_LAUNCH, ..., CE_SET_SEMAPHORE, CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE]`
        - 每一对`(dst, src)` pair都变成了一次`CE_DMA_LAUNCH`（CE指Copy Engine）
        - 最后会设置一个用户不可见的semaphore并且做一次memory release fence
    - 然后一次Doorbell
- 然后`cudaEventRecord`变成了
    - 一个新的GPFIFO entry，属于Compute的channel
    - 一组PushBuffer的commands，简单来说包含`[GPFIFO_WAIT_AND_ACUQIRE_SEMAPHORE, COMP_SET_REPORT_SEMAPHORE_AND_RELEASE]`
        - `GPFIFO_WAIT_AND_ACUQIRE_SEMAPHORE`负责等待`cudaMemcpyBatchAsync`的完成
            - 注意CUDA Stream被UMD翻译成了跨Channel的同步
        - `COMP_SET_REPORT_SEMAPHORE_AND_RELEASE`这里写入到一个用户可见的semaphore里，可以用`cudaEventQuery`读取
    - 然后一次Doorbell
- 这里可以列一个表，左边那列是API call，比如`cudaMemcpyBatchAsync`，中间一列是产物，右边一列说明是哪个channel

### Oppotunies

- 对于我们的需求，以先用Copy Engine复制chunks，然后用RDMA发送chunk为例子，我们可以构造这样一个PushBuffer的commands
    - `[CE_DMA_LAUNCH, CE_SET_SEMAPHORE, CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE, CE_DMA_LAUNCH, CE_SET_SEMAPHORE, CE_DMA_FLUSH_AND_RELEASE_SEMAPHORE, ...]`
    - 也就是说我们对每个chunk进行一次DMA Copy，然后立刻设置SEMAPHORE，并且做一次memory release fence
    - 我们已经验证了由Copy Engine对semaphore的变更是Host CPU可见的，本来这个semaphore就是在Host memory上（可能GPU也cache了）
    - 由于PushBuffer的command是顺序提交给Copy Engine（但不一定顺序完成，所以我们加了fence），我们可以Copy Engine设置写入semaphore的值为完成的chunk的序数
    - CPU poll这个semaphore，只要发现这个序数变动了，我们就可以提交RDMA操作了

## Our Solution

- 由于CUDA官方并没有提供手动管理channel和构建PushBuffer command的方法，因此我们需要实现能和CUDA Runtime和UMD兼容的shim layer，通过直接与开源的kernel驱动沟通，实现我们需要的功能
    - 然而这并非不可能的任务，`geohot/cuda_ioctl_sniffer`已经实现了完全绕过CUDA UMD而提交CUDA计算程序
    - Vulkan这样的图形栈也有社区维护的开源userspace驱动NVK维护PushBuffer，社区的开源内核驱动nouveau维护GPFIFO（和NVIDIA官方的开源内核驱动`nvidia-open`不是一个东西）的先例
- 然后这个shim layer负责将Copy Engine和RDMA的事件bridge起来
